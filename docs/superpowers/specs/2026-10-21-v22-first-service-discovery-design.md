# P3 首次服务竞品准备与单次点数衔接

继续执行已批准主计划 §8，不改变 D1，不开放付费入口。本批交付内部事务边界；前端向供应商提交、后台自动对账和用户确认界面仍需后续连接。

## 调查结论

旧竞品发现预留 Prospect 点数；首次服务准备则在确认竞品后预留 Verified 点数，直接串联会重复收费。现有 BusinessScope 要求至少一个竞品，不能在发现前虚构业务确认版本。发现有独立任务、结果有效期和重试；报告处理期限为 20 分钟，不能把人工等待时间算作报告处理失败。

## 本批实现

1. 新增服务专用发现准备登记。使用已保存的 Case 身份、服务、地区、3–5 个查询和两份就绪的 GSC/GA4 快照检查资格，再原子预留一次 verified 点数。此时不建立报告或分析任务，不要求虚构竞品。请求、任务 ID 和原始来源引用固定，响应丢失只能用相同请求恢复。
2. 内部服务在核验后登记实际发现结果；结果引用和候选网址必须持久化，不接受浏览器自报成功。记录结果前有独立 20 分钟技术处理期限；保存结果后进入等待确认，不因用户停留自动退款。零候选不是零行动报告，不允许进入生成。
3. SEO 确认竞品并形成业务版本后，原启动事务识别这份预留，校验 Case/身份/查询范围及候选有效性，重新检查当前私有来源，再建立原 first_service 任务。工作流 ID 固定为后续任务 ID，预留账本不改写、不重复扣点；生成处理期限从此时开始。
4. 采集登记必须引用同一发现结果和查询，防止换入另一份发现、市场或竞品。下游仍执行真实发现核验、租约、固定来源及正式报告结算。
5. 已明确失败或未保存结果的技术准备超时，可由内部事务结算一次返还。结果已保存、任务已绑定或正常完成均不可从准备阶段返还。后台调用者不得把 HTTP 超时、暂时未知状态或用户未操作当成明确失败。

## 边界与后续

只提供服务端仓储和 SQL 边界，所有 RPC 对 anon/authenticated 撤权；不修改旧 Prospect 收费、不启用真实功能开关。保持当前服务采集器的 mobile/en 市场默认值，不接受其他设备/语言后再静默变换；首个发现请求不接受补充网址。发现重试沿用原任务与请求；重新发现、过期结果刷新及人工补充的同点数多任务协调、后台轮询/对账、页面付费确认及完整生产环境验收继续后续实施。在这些接线完成前不能开放预留 RPC 到浏览器。

回执明确区分 discovering、needs_competitors、awaiting_confirmation、analyzing、completed、failed。成功搜索但没有候选进入 needs_competitors，不创建诊断报告、不伪装成技术失败；是否可以生成仍由完整候选和私有来源校验决定。准备时的来源引用用于审计；正式分析开始前允许更新已过期的私有数据，启动后继续按原规则固定来源，不能执行中替换。

## 验证

运行全部迁移的隔离数据库：无 Prospect/无业务版本启动、一次扣点、重放/跨用户/变更请求拒绝、资格失败零扣点、并行流程互斥、候选确认和来源复核、绑定不二次扣费、技术补偿一次、等待不补偿、迟到结果拒绝、完整零行动交付消费一次。服务端仓储测试输入校验、错误脱敏、回执身份及字段白名单。PGlite 不替代原生 PostgreSQL 多连接锁竞争、真实 Google/Redis/身份/供应商验收。
