# P4：确认重点、冻结条件、受约束调序

已批准依据：总执行计划 P4、上一批明确的后续范围及用户“可以开始吧”。本文件记录实施选择，不重新要求批准，不提交脏工作区。

## 范围与流程

Case 保存可选业务目标（服务可见性/联系路径/业务身份/未知）、最多 20 个同业务网站目标页面，以及独立 SEO 的执行容量（未知/有限/可安排）和发布权限（未知/需审批/可发布）。不用营收评分或未经确认的工时估计，不引入另一位执行者。

设置免费保存，使用版本号避免覆盖别的页面。它们在获客开始报告分析、或首次服务确认竞品并准备诊断时，和业务范围一起冻结；之后改动只影响新分析。开始时携带已看过的设置版本；版本不一致不得静默替换。响应丢失后已登记任务优先恢复，不因新设置拒绝恢复。

界面采用紧凑、可选的单个表单，清楚标注未知及保存状态；未保存或状态不明时不能确认生成。新入口受默认关闭的独立设置开关和已有 capability 开关共同保护，现有入口开关不修改。

## 规则与历史兼容

新增生成规则 v3 / 排序轨迹 v2；保留 v1/v2 生成器及轨迹 v1。BusinessScope 的执行条件可选，历史序列化不新增空键，摘要不变。新排序只在已确认条件下调整执行确认状态及平级顺序；前置、业务相关性及证据等级不被可投入时间覆盖。

新轨迹 v2 的交付顺序必须保留每项显式依赖，并保持访问/索引、测量可靠性、其它工作的层级先后。界面提供上移/下移、不可移动的原因和恢复系统顺序；恢复仅改顺序，不丢失文字。Python、TypeScript、SQL 保存均验证同一约束。旧轨迹/旧已批准修订不追溯应用新约束。

## 持久化与验证

新增 Case 设置表及服务端授权 RPC，直接客户端角色无读写权。已有业务范围/输入/报告/修订不更新；只新增版本。数据库冻结及版本检查保持同一事务、同一 Case 锁；首次服务沿用连接→Case→工作流的锁顺序。新设置不改变一次收费、零行动正常消费和技术失败一次返还。

覆盖设置合法性、同域 URL、越权、原点/大小限制、并发版本冲突、响应丢失重放、冻结后修改不影响原报告、不同执行条件、历史摘要、依赖调序与恢复、批准/分享/PDF 一致。迁移仅在隔离数据库验收，保持未部署。
