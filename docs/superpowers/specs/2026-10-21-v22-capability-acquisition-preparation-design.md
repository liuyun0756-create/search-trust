# 获客采集到冻结输入：P2 接续设计

承接已批准执行计划。本批不修改营销页面、不开放首次服务或生产入口、不再次收费、不提交或部署。

## 范围

1. 为已经预留一点的获客任务登记不可变准备记录：owner、Case、原任务/幂等键、已确认业务版本、经校验的获客请求。登记不创建新账单、不延长截止时间。相同请求重放一致；改变请求或业务版本必须拒绝。
2. 服务端准备协调器先取得登记回执，再复用现有发现结果和采集阶段；冻结完整输入后返回上一批 dispatch 所需的小 envelope。准备成功后响应丢失，重试先读取 SQL 已准备回执，不能再次采集或覆盖输入。
3. 采集输入桥接器核对业务、客户页面、已确认竞品、搜索上下文及公共商家来源。site/competitor 仅接受本任务开始后采集的内容，其有效期保守限制为原任务 deadline；不为历史无有效期快照重新计时。SERP/公共 GBP 沿用原来源有效期。
4. 原到期巡检扩展到有明确新版准备记录但尚无 manifest 的任务。数据库当前时间和原 deadline 为准；技术失败原账单补偿一次，完成报告不返还，未知网络结果不立即退款。

## 边界和验收

- 只做 acquisition；first_service/after_acquisition 不从此通道进入。真实首次服务入口另行实现。
- 使用现有采集器接口、检查点和成本账本；不新增模型或供应商，也不增加采样预算。
- 纯输入构建不构成授权；SQL 登记/冻结分别复核所有权、扣点和来源。原始快照不能被修改以适配契约。
- 测试覆盖准备前失败、错误身份/业务/请求、重放、过期、不合格/串客户来源、准备完成但响应丢失以及零行动仍交付的实际规则生成。
- 新用户入口的创建/预留/确认界面及配置注入仍需随后衔接。本批协调器不自动改接旧 API；默认关闭状态不变。

## 接续实现约束

- 准备阶段复用 `ProspectV22Executor.collect_sources`，不调用旧报告生成/持久化。原 `execute` 继续依次采集与生成旧报告，保留旧调用接口。
- 已登记准备任务不得附加旧报告 ID；manifest 必须匹配登记业务版本，recipe 必须匹配登记的业务身份、查询、地区与竞品。
- SQL 已记成本但 Redis 操作账本丢失时，停止采集并等待恢复；完整成本字段集合继续沿用既有模型。
- 本批不创建准备 worker 的 Redis 状态/租约。接入时要有独立准备阶段队列身份和检查点状态，沿用同一逻辑任务、原代次、原 deadline 及成本账本。不能把旧完整请求登记进正式执行队列后，再用同一任务强行替换为新版小 envelope；现有存储会按身份冲突拒绝。
- 准备 worker 必须沿用原 deadline 的运行超时与成本回调，不能只依靠输入构建后的截止时间检查。真实入口应原子化处理预留/登记的失败边界；登记前已扣点但没有标记的窗口仍未由本批巡检接管。
- SERP 继续使用已确认发现记录的来源标识。不同 Case 不得借此强行复用同一个已绑定数据库快照 ID；若共享缓存命中跨 Case，后续入口须完成 Case 级安全持久化设计，不能通过修改原始来源引用绕过冲突。
