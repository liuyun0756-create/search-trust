# P2 接续：报告列表、编辑与批准接入

依据已批准的 v2.2 主执行计划 §7 P2-03，以及用户“开始下一步”的接续授权。本批实现既有编辑/阅读组件的正式接入，不重新设计营销页面、生成器或收费机制。

## 调查结论

- 新报告落库与完成结算已有独立门槛；原列表只读取旧 reports 表，不能展示 capability_report_versions。
- owner 页面已能读取新版原始/批准报告；编辑组件和修订存储已有但未挂载。
- 原修订存储原语接受尚未结算的候选报告。正式用户保存不能直接暴露该原语，必须新增完成门槛，并收回绕过门槛的 service_role 执行权限。
- 修订号是乐观锁；最新草稿不能成为批准交付，旧批准版本不可变。已有 SQL 原语负责内容限制及证据不变校验。

## 接入决策

1. 保持既有 `/reports` Case 工作区。开关开启时，合并完成/消费门槛筛选出的新版轻量元数据；不加载整份报告来生成列表，不把候选或失败任务展示为完成报告。任何来源读取失败显示错误，而不是假装没有报告。
2. 新的 content-revision 接口与旧三行动 delivery-plan 接口隔离。GET 返回最新完整可编辑内容及下一次保存预期号；PUT 保存草稿；POST 接收明确审阅确认后保存批准修订。身份从服务端获取，Case/report 来自路由，正文中的身份、来源摘要和不可编辑部分必须一致。
3. SQL 新保存包装函数再次检查正式报告资格，然后调用原不可变修订存储。原语仅由数据库内部调用，普通 server role 不能绕过完成门槛。保存和批准不触发分析或点数操作。
4. 页面先展示原始报告；可选编辑置于次级展开入口。既有草稿完整恢复；批准无需先修改或保存草稿。批准复选框在内容变化和保存后重置；交互未就绪时不允许提交。
5. 客户阅读仍只使用最新批准修订；后续草稿不冒充批准结果。刷新页面更新状态，但不以 revision 为 key 强制卸载未保存编辑器；并发冲突保留输入并提供复制。
6. 写请求限制为 JSON 且最大 100,000 字节，拒绝跨站来源与多余顶层字段；读取/写入响应不缓存，错误不回传数据库或客户正文。

## 本轮不包含

新版 PDF 下载/分享端点、持久品牌设置、首次服务用户入口、实施复核、真实第三方数据验收、生产迁移及部署。功能开关不启用；不把本批测试称为 P2 整阶段完成。

## 验证边界

完整源迁移在 PGlite 中验证候选不可见/不可编辑、owner 隔离、零行动原样批准、修订冲突、后续草稿、旧修订不变与不再扣点。接口和仓库分别验证权限、内容、回包和安全失败；组件模拟请求覆盖保存/批准及输入保留；报告列表检查开关与错误状态。生产构建与旧报告/分享浏览器回归补充兼容检查，不能代替真实 PostgreSQL 多连接和新版浏览器全流程验收。
