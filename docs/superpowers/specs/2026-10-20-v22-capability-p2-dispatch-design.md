# P2 接续：已准备任务的提交与报告定位

承接已批准主计划与 worker 分支。本批完成已冻结、已预留一点的任务从 owner API 到内部队列的实际派发；不把它当作新客户采集/收费入口，也不启用开关。

- 用户请求只有 Case、原任务 ID、原幂等键和空对象。服务端从数据库读取原冻结 envelope，不能由浏览器指定来源、报告类型、用户或摘要。
- 新服务端 RPC 同时检查 owner、Case、任务、manifest、recipe、原幂等键、有效来源和原扣点。成功结果允许按已消费权益返回，不要求历史来源仍有效。
- 内部提交再次读取并校验绑定；Redis 只保存小 envelope，初始代次、创建时间、截止时间沿用 SQL，重试不延长预算、不重扣、不复活失败任务。
- 登记成功但 enqueue 响应丢失时，同一请求可再次投递同一物理 ID；ARQ 去重。已运行或已完成不主动重新排队。网络不确定不能自行退款，原 SQL-first 终态恢复继续负责。
- 默认关闭 FE 提交开关；BE 要求现有新版执行 readiness 和已注入输入仓库。旧 analyze、verified-analyze 保持兼容。
- 状态接口识别新版完成引用，核对任务与 Case；读取新报告必须再次通过 completed/consumed owner 权益。未结算候选不可见。

验证覆盖：错误 owner/幂等键/未准备/过期/已失败、相同请求重放、队列写入前后断线、SQL 完成但 Redis 不可用、原截止时间和代次、旧请求兼容。新来源采集、首次服务收费 UI、导出/分享仍单独验收。

## 恢复与预算约束

- SQL 已记录成本、Redis 操作成本账本却丢失时，不能用汇总计数重建空账本继续执行；拒绝重新派发并等待安全恢复或原截止时间处理。原尝试预算耗尽也不因重新提交获得新预算。
- 新增每分钟的已准备任务巡检。仅按数据库当前时间处理已冻结 manifest、queued/running、原 deadline 已到且没有正式完成报告的任务；调用原失败事件与收费补偿，最多 100 项，使用行锁和 skip locked。
- 未进入 worker 的任务保留实际 attempt_count=0，不为了通过终态接口伪造一次尝试。补偿仍在原事务事件内完成，重复巡检不重复返还；已成功交付的零行动报告不被选中。
- 巡检随新版执行 readiness 注入，默认不运行。开放真实任务前仍需排空/独立恢复开关方案；关闭开关不等于自动取消或退款。尚未冻结 manifest 的准备失败不在此次巡检范围。

## Owner 阅读

旧报告读取优先且不改变旧数据。新报告读取同样默认关闭，并先验证 completed/consumed owner 权益；系统版始终展示不可变原报告。仅最新修订已批准时提供对应客户版；最新修订为草稿时提示未批准，不偷偷回退到较早批准版。此处不是新版编辑、PDF 下载或固定分享入口。
