# 共享搜索来源与客户绑定分离

承接已批准的能力补齐计划及获客入口下一步。本次只修复新版来源准备中的跨 Case 共享搜索缓存冲突，不开放新入口、不改变收费及缓存过期政策。

当前问题：SERP 原始共享 snapshot ID 被直接作为 `data_snapshots` 主键，后者同时要求唯一 Case。第二个 Case 合法命中同一共享缓存会因归属不同而失败。

采用独立引用而非改写来源：

- 新获客输入的 SERP binding ID 用 UUIDv3(URL namespace, `searchtrust:capability:serp-binding:{case_id}:{source_id}`) 确定生成。该 ID 仅代表客户存储引用，不代表重新抓取。
- shared snapshot 的原始 ID、source job、校验值、采集和失效时间及完整原始数据不变；竞品来源中的 market snapshot ID 也保持不变。证据解析支持精确的 Case-local ID，并兼容已有直接引用。
- 数据库新增不可变来源登记与 Case 引用关系；同一个来源 ID 不能换数据、来源任务、输入摘要或有效期。数据正文仍按 Case 存储，不允许用户通过全局表读取其他客户。
- 新的准备 RPC 外层执行归属/任务校验及来源绑定登记，再调用原准备事务；任何后续失败全部回滚。旧 recipe、旧报告和私有授权来源不迁移、不改写。
- SQL 与 Python 使用相同 ID 派生算法；正文完整性继续使用 SHA-256，UUIDv3 不承担安全哈希用途。
- 发现缓存原来只按查询摘要生成来源 ID，过期后的新采集可能沿用旧 ID。新写入的来源 ID 纳入原始 payload SHA-256（包括来源任务和采集时间）；缓存查找键不变，有效的旧缓存原样返回，历史内容不迁移。

验收：同源跨 Case 成功、原始数据/时间不变、独立报告证据引用、重放不重复收费；伪造绑定、改变原始来源/有效期、跨 Case 引用及私有来源共享均拒绝。PGlite 与 FakeRedis/合成来源只作为本地分层验证，不宣称真实生产并发通过。
