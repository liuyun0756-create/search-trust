# 获客准备队列接续

沿用已批准的 v2.2 执行计划和获客准备设计。只接内部队列，不启用开关、不切换旧用户入口、不部署。

- 准备使用独立 ARQ 函数和物理 ID；队列只携带原 job ID / generation，不复制客户来源到队列参数。
- SQL 准备租约是权威：领取时核对原登记、收费、状态、代次和截止时间；原任务 attempt_count 同时计入准备与正式执行，不能获得两套重试预算。
- 独立准备检查点沿用原 job ID / generation，成本账本仍使用原任务的 key。领取后曾执行过的任务若账本丢失，停止采集，等待恢复/截止补偿；运行中账本丢失也不能默默重建。
- 心跳刷新租约并保存成本；失去租约或原截止时间到达时取消采集。冻结输入必须携带有效租约，旧 worker 不能在接管后提交。
- 冻结前记录成本并原子移交：manifest/recipe 与最后准备成本一并提交；随后调用既有正式 dispatch。移交失败重试直接读取已冻结输入，不再采集。准备阶段不发报告完成回调。
- 未知 RPC 结果不立即返还；准备失败和无 worker 的任务继续由已有 SQL 原截止时间巡检兜底。正常无行动报告仍消耗一点。
- 测试覆盖重复领取、失效租约、旧代次、尝试耗尽、准备提交/排队响应丢失、成本丢失、超时取消、同任务交接以及旧链回归。真实 Redis 重启和原生 PostgreSQL 并发仍属于发布门槛。

本轮不完成新建分析的业务确认/原子预留 UI、首次服务、批准/导出/分享；这些仍在主计划中继续，不以内部接入替代用户验收。
