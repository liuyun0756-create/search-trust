# P5-03 第一批：复核依据与报告判断

状态：2026-10-26 用户已确认分批范围及书面设计；本地内容层实现与验证完成。见同日 `2026-10-26-v22-capability-p5-review-projection-verification.md`。未接收费生成、未部署。

## 1. 目标和范围

让一次复核清楚回答：SEO 记录了什么工作、页面检查发现什么、所选期间的数据怎样变化，以及下一阶段还有什么需要决定。

采用独立、可重复计算的复核依据包与报告内容投影。第一批交付内部数据契约、校验、确定性组装、行动关联、语义差异及测试，不开放收费复核入口。

本批不生成可交付的新 Verified 实体，不创建报告编号，不启动任务，不写入点数账本，不更新旧报告、PDF 或分享。它为第二批接入新版 Verified 提供已经验证的内容层，不是第三种报告商品。

本批的“冻结”指完整输入的规范化序列化、版本绑定和校验和，以及脱离可变原对象的计算；不宣称已完成生产数据库的原子冻结。后续接线必须从所有者有权读取的存储组装并原子保存该输入，不能把本批的纯函数或 checksum 当作授权证明。

### 已选择的方案

1. **采用：先实现内容与判断规则，再连接收费生成和交付。** 先验证报告不会混淆实施、观察和效果，兼容既有来源与账本。
2. 延后：一次接通所有生成、结算、版本和交付环节。验证范围过大，不纳入本批。
3. 不采用：只给旧报告增加前后数字。不能回答下一步工作，也无法固定判断依据。

## 2. 已核实的现有约束

- `capability_input_repository.py`、`capability_result_persistence.py` 及现有派发授权主动阻止 review。保持这些保护，不为了运行本批而删除。
- `CapabilityReport` 2.2.2 的 evidence 引用普通来源快照。页面实施观察、专用比较和 GA4 会话阅读不能伪装成普通快照插入原契约。
- `ImplementationRecord` 绑定上一份 Verified 和已批准的交付修订。实施条目只有行动、范围、实施日期、时区及备注，没有验收完成状态。
- 页面检查只检查静态响应中的指定文字、链接或锚点，不能证明渲染、业务正确性、联系路径实际可用或 SEO 效果。
- GSC 比较仍是描述性比较，指标效果资格待校准。GA4 会话阅读有独立 available/withheld 状态，不改变原资格，不证明处理终结或历史配置未变。
- 既有 GA4 人工检查是 SEO 声明，不是人工解锁数值或效果的开关。

## 3. 输入契约：固定什么

新增独立 `v22_review_evidence_bundle_v1`，不修改旧输入版本。

### 3.1 核心输入

- 当前用户与 Case 标识、固定的 `evaluated_at` 和规则版本。
- 上一份完成的 Verified 完整内容、报告 ID、版本及 checksum。
- SEO 已批准的交付完整内容、交付 ID、修订及 checksum。行动标题、范围、步骤等以这份已批准内容为工作基准，不退回原始生成文案。
- 一份精确的实施记录 ID、修订、checksum 和完整内容；允许合法空条目，不伪造实施日期。
- 按已批准行动排列的显式来源选择，及可选的 SEO 下一阶段决定。
- 整份输入的规范化 checksum；计算时重新解析完整内容，不信任可变模型实例的旧校验结果。

新复核的 `evaluated_at` 不替换旧比较的评估时间，也不使原来尚未结束的窗口自动变为可用。

### 3.2 每项行动的来源选择

每个既有行动最多选择：

- 一组页面检查：当前 observation，以及可选的之前 observation；保留原 plan、绑定、条件和结果。
- 一份已保存的 GSC FrozenComparison：完整 selection、request、result 和原来源引用，复用现有重算验证与数值阅读。
- 一份已成功保存的 GA4 collection：完整原观察与绑定，用既有 `read_sessions` 重算阅读；不接受单独提交的 before/after 数字。

没有选择来源时使用显式 null。缺失不代表零、不代表失败、不代表没做工作。界面尚未提供选择功能，本批不新增入口；调用方未来只能传所选存储 ID，由服务端读取内容。

不自动选择最新记录，不从实施备注猜 URL，不因 URL 相同而把一个行动的来源搬到另一个行动。不同来源允许使用不同窗口，但必须分别显示，不能合成一个“统一前后周期”。站点级数据不改写成页面效果。

GA4 人工核实记录、附件、外部备注和自由文本来源不纳入本批证据包；保留原位置与权限，不自动进入报告或模型上下文。

### 3.3 绑定、时间与体积

- 校验 user、Case、报告、交付、实施修订、action 和各来源原有身份绑定。任何冲突都拒绝整个输入，不悄悄省略冲突来源。
- 复用既有域名规范化规则核对 GSC 属性与 GA4 hosts 是否属于已批准业务的网站范围；同 Case 标识不能代替网站范围一致性。只支持现有根属性范围，不推断其他子域或 URL 前缀属于同一业务。
- 页面前后观察复用既有比较器；不同 plan 的合法观察只能得到不可比，不能忽略条件差异。
- 所有输入必须在固定评估时刻已经形成；来源自身的时间顺序、窗口及完整性继续由现有验证器检查。
- 已批准行动最多 3 项；每项每类来源只选一份或一组，不构建无限历史列表。
- 规范化输入总量上限 2,000,000 UTF-8 字节；超限明确拒绝，不截断证据。来源保留现有更严格的字段上限。
- 重新序列化与校验后取得独立内容，调用方随后修改原对象不改变已构建输出；不依赖浅层 frozen 标志保护嵌套列表。

## 4. 输出：四个部分，不混合事实层级

独立 `v22_review_projection_v1`，带输入 checksum、规则版本和来源引用。所有效果字段固定为 null，因果资格固定为 false。

### 4.1 本期实施 · Recorded work

列出原行动、批准后的工作范围、记录的实施日期和 SEO 备注。来源类型为 `seo_recorded`。

示例：`Implementation recorded for 12 October. Scope: clarify the repair service and contact step.`

没有条目：`No implementation record was selected for this action.`

不使用 `Completed` 或 `Verified implementation` 作为自动状态；没有记录也不写成“未实施”。

### 4.2 页面核实 · Page checks

分别展示目标 URL、检查时间、条件及 observed/not_observed/unable_to_check。前后都有效且符合原比较规则时，展示条件的 newly_observed/no_longer_observed/unchanged。

首次检查：`First recorded check. There is no comparable earlier observation.`

命中条件：`The selected contact-link condition was observed in the static page response.`

不能据此写成“联系路径已修好”或“页面已全面完成”。未找到条件只表示这次静态检查未找到；检查失败保留原因，不等于条件不存在。页面 HTML checksum 不同也不自动代表行动完成。

### 4.3 数据变化 · Selected-period figures

- GSC：复用原 comparison 和 metric reading，展示允许的 clicks、impressions、CTR、前后日期、范围、分母与限制。
- GA4：仅复用已允许的 sessions 数值阅读；available 才显示数字与差值，withheld 保留原因，不能从原快照绕过规则取数。
- 数值正、负、相等只描述方向，不标记成功、失败、改善、损失或统计显著性。
- 前期零值不生成百分比；无基线不能生成改善；不拼接 GSC 点击与 GA4 sessions 计算转化率。
- 不选择性隐藏负向结果；合法来源被选入后，无论方向或受限状态都进入投影。
- 明确保留 GA4 处理终结未证明、测量历史未验证以及 GSC 效果资格待校准等原有限制。

### 4.4 下一阶段 · Next decision

拆成两层：系统生成的核实事项，以及 SEO 明确记录的工作决定。两者不能混成“算法已证明的下一步”。

系统核实事项使用固定规则、有限代码和模板：

| 事实 | 系统可以提示 | 不能自动判定 |
| --- | --- | --- |
| 无实施条目 | 确认实际做了什么及日期 | 未实施、继续执行 |
| 无页面检查或首次检查 | 建立或补充对应检查依据 | 页面已改善 |
| 条件未找到、检查失败或不可比 | 人工检查该条件及检查限制 | 整项行动失败 |
| 窗口未结束 | 等待原定窗口完成后再安排采集 | 现在已有效果 |
| 数据缺失、受限或不可比 | 说明具体来源限制及需核实项目 | 数据为零或工作无效 |
| 合格数值有变化或不变 | 在原范围内描述数字；保留其他解释 | 仅凭数字决定调整工作 |

核实事项不是新增付费行动，不占用报告的三项工作名额，也不自动触发采集。

## 5. 下一阶段行动分类

本批不新增“已验收完成”的产品能力，不从自由文本猜完成状态。输出的 `decision_state` 为 `needs_review` 或 `seo_recorded`，后者才带下列 disposition。没有决定时 disposition=null，不默认填“继续”。

SEO 决定作为独立、有界的结构化输入：绑定本次证据选择 checksum、记录时间、原行动 ID（新增除外）、分类、非空理由、引用的证据 ID；调整或新增还须有明确的目标和拟做工作。证据选择 checksum 覆盖核心输入及所选来源，不包含 SEO 决定；整包 checksum 再覆盖决定，避免循环依赖。理由和完成声明各最多 1,200 字符，目标最多 2,000 字符，拟做工作最多 4,000 字符，引用最多 12 个且不得重复。它是内容层输入，本批不新增保存表、API 或编辑界面，后续必须由已认证的保存流程提供。

| 分类 | 含义与必要条件 | 输出来源 |
| --- | --- | --- |
| continue | 继续原行动；必须保留原行动 ID 和理由 | SEO 决定，不由数字自动推出 |
| adjust | 调整原行动；须有原 ID、调整后的范围/工作、理由及至少一项所选依据引用 | SEO 建议，原行动不被覆盖 |
| observe | SEO 认为所述工作已完成并选择观察；须有对应实施条目及明确的完成声明 | 标注 SEO 声明，系统验收仍未证实 |
| defer | 暂缓；须有原 ID、原因及重新考虑的条件 | SEO 决定，不写成工作无价值 |
| new | 新增工作建议；须有新 ID、目标、工作、理由及至少一项所选依据引用 | SEO 提议，不能标成系统已验证的建议 |

引用存在只证明可追溯，不能证明自由文本理由正确。所有决定显示 `SEO-recorded decision`，不提取自由文本中的效果主张作为系统结论。安全展示按纯文本处理。

每个既有行动最多一个决定。新增最多 3 项，ID 不得与原行动或其他新增项冲突；下一阶段非 defer 的计划项总数最多 3，needs_review 不自动占用已确定计划名额；defer 仍出现在原行动复核记录。超额拒绝并要求明确优先级，不静默丢弃。

本批没有自动新增工作发现引擎。没有足够依据时，保留完整诊断内容和待决定状态，不补齐三个行动、不制造建议。后续若需要系统自动提出新行动，必须连接已有合格发现/候选规则并单独验证，不能拿 SEO 的输入冒充系统发现。

## 6. 语义差异与版本

完整输入/输出 checksum 用于完整性；单独的语义指纹用于判断内容是否变化。二者不可混用。

- 首次投影没有同版本前次投影时为首次基线，不显示改善或“新增了所有内容”的徽标。
- 对照必须属于同用户、Case、原报告、批准交付及同一投影规则版本。不同基准或规则版本返回不可比，不猜行动对应关系。
- 逐原行动 ID 比较批准后的工作内容、实施记录的业务内容、页面条件状态、数值及范围/窗口、限制、核实事项和 SEO 决定。
- 时间戳、记录 ID、checksum 或重复采集次数单独变化不触发结论变化徽标。若实施日期、数据窗口或范围改变，这些是有意义的内容变化，必须明确展示。
- 分别输出 evidence_changed 与 decision_changed；数字改变但工作决定没变，不显示“建议已调整”。
- 限制由可用变为受限、条件由命中变为未找到也属于内容变化，不能只标记正向变化。
- 保留可核查的具体差异，不以纯自然语言相似度或模型推测判断。

## 7. 未来两个阅读层的内容投影

本批生成结构化内容，不实现新页面、PDF 或分享。

客户摘要保留：本期记录的工作、能核实的观察、允许展示的数据与关键限制、下一阶段决定或待确认事项。不能因简化隐藏“未完成核实”、数据受限或 SEO 声明来源。

SEO 明细保留：精确行动/来源绑定、窗口与范围、条件结果、所有受限原因、核实事项和差异详情。owner ID、内部校验和、内部错误或私人备注不默认进入客户摘要。

两个投影来自同一份已验证输入，事实、数值和限制不能冲突。未审核的自由文本仅在 SEO 明细标记为记录内容；客户摘要使用受控字段和模板，不能自动把私人备注或未审核决定理由发布出去。

## 8. 模块边界与错误处理

建议后端按职责分为：复核契约/绑定验证、来源适配、四部分组装、决定校验、语义 diff。沿用 `app/report_v22/` 结构，不改造无关报告流水线。

复用现有实施校验、页面比较、FrozenComparison 重算和 GA4 阅读；不得复制一套更宽松的资格算法。前端仅接收导出的契约与确定性测试样本，本批不增路由。

缺少某类可选来源：合法投影并给出缺失状态。来源合法但受限：保留原受限状态。畸形来源、checksum 不符、跨身份、未来来源、重复冲突 ID、无效行动引用、超限：拒绝整个投影，返回有限错误代码，不回显源数据或任意异常信息。

纯构建层不进行网络、数据库、队列或模型调用。checksum 是一致性校验，不是可信签名；本批构造测试通过不等于生产授权入口已完成。

## 9. 验收条件

实施前保存两仓工作基线；不覆盖已有未提交改动。

1. 同一固定输入重复构建得到相同输出；修改原嵌套对象不会污染已构建结果。
2. 报告、交付、实施和各来源错配、篡改、超额、超长、未来时间一律拒绝；合法缺失不会导致伪造值。
3. 已批准编辑后的行动是基准；原始生成文本不同也不恢复原始版本。
4. 空实施记录、首次页面检查、失败/不可比检查、条件增减及重复检查均输出准确状态。
5. GSC 与 GA4 覆盖正向、负向、不变、前期零、双零、缺失、受限、窗口未结束及不同范围；不把描述性数字升级为效果。
6. 三行动互不串来源；站点范围不改写为页面范围；不同数据窗口不合并。
7. 五类 SEO 决定和 needs_review、无理由、无原行动、无实施却声明 observe、错误依据引用、超额计划均有定向测试。
8. 同结论重复证据无决定变化徽标；范围、窗口、资格、条件或决定真实变化能逐项解释；无可比前次投影只建立基线。
9. 客户/SEO 内容一致；私人备注、内部身份、原始错误不泄漏到客户摘要；没有证据时不强行生成建议。
10. 新契约双端导出一致；旧 schema、checksum、GSC/GA4 资格、旧报告和点数测试保持通过。
11. 验证纯构建层无 provider、数据库、队列、模型和扣费副作用。无 UI/路由/迁移修改时，不把不存在的新浏览器或数据库流程列为已验收。
