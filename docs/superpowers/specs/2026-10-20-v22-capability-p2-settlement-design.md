# P2 接续：新版报告完成与一次结算

本批执行已获批准的主计划 §1.2、§6.3、§7 及 D1，不新增商业决定、不开放入口、不部署。沿用已确认的零行动正常交付消耗一点、技术失败返还、内部重试不重复扣点。

## 现状与选择

2.2.2 候选产物已保存到 capability_report_versions；旧任务 report_id 和 workflow_charges.final_report_id 只引用历史 reports。不能创建虚构旧报告壳，不能把候选保存直接解释为成功，也不能把应用层两次写入当作原子结算。

采用增量的 capability_report_id / final_capability_report_id，保留旧外键，约束新旧引用互斥。一次服务端完成 RPC 在事务内校验冻结依据、任务代次、归属及已有一点扣账，保存不可变报告、关联任务成功、消费原收费记录。既有终态触发器兼容两种报告；新入口尚不挂载。

## 完成不变量

- 正常结果可以 0–3 项行动；不根据行动数量返还。
- 只有 queued/running 当前代次、reserved 且有原始一次扣账、无返还的任务可完成。
- 同一任务、代次、完整 payload 重放返回同一报告和校验值；异内容、旧代次、跨用户、已失败/返还拒绝。
- 任务、候选、收费的修改失败时整笔事务回滚；候选存在但任务未成功不构成交付权益。
- 成功后迟到失败回调、直接状态倒退或补偿均不能造成报告与返还并存。
- 允许失败任务保留内部候选用于诊断，但读取完成报告和使用新版父报告必须验证完整成功/消费关联。
- 不自动批准客户交付修订；正常交付系统报告与 SEO 批准修订是不同状态。

## 边界与实现

新增迁移提供事务完成 RPC、仅服务端的完成报告读取 RPC、终态与收费关联防护。复用旧失败返还逻辑，不触碰付款退款规则。后端新增受限持久化适配器，调用前重新验证完整报告与预期 manifest，使用现有有界、禁重定向、错误脱敏的 RPC 传输；不在本批挂载旧 worker。前端新增显式 loadCompletedReport，原 loadReport 仍只是内部候选读取，不可作为下载或分享权益。

验证包括：0–3 行动、重复完成、丢失响应后重放、保存失败回滚、代次替换、完成/失败两种先后次序、迟到回调、跨用户、缺扣账、已返还、候选不可交付、历史权益、旧迁移回归。隔离 PGlite 能验证事务和不同提交顺序，不声称验证真实多连接行锁竞争；若未提供隔离 PostgreSQL，该并发门槛留待后续发布验收。
