# 获客开始分析入口接续

沿用批准的 v2.2 计划。现有工作流在开始竞品发现时已预留一点，本批不改变扣点时机、不新增第二次消费。

1. 保留现有业务/竞品确认界面及请求，服务端默认关闭的新分支跳过旧的单独 bind，转发经过身份认证的内部获客入口。关闭时旧流程保持不变。
2. 内部入口先检查 owner / Case / 已预留 workflow / discovery 关联。首次请求再验证发现结果与选择的竞品；将业务确认版本、原额度绑定的分析 job 和准备标记放进同一 SQL 事务，失败全部回滚。
3. 重放先按保存的完整分析请求、发现 ID、原 job/key/workflow 校验，不依赖已过期或丢失的 Redis discovery。准备/排队响应丢失后仍重用原任务；不同请求拒绝，不降级到旧链。
4. 已登记任务从 SQL 返回安全的排队/准备/生成/失败状态；完成只返回已有新版报告引用。页面沿用现有轮询解析，准备期不依赖尚未建立的正式 Redis 状态。
5. 任务恢复继续使用已有 Case 的最新任务查找，完成状态返回独立的新版报告引用，不填入旧报告 ID 字段。Case 报告列表索引后续单独接入。新路线受原 capability 开关及新增默认关闭的 intake 开关约束，未启用或部署。

不解决用户停留在竞品发现、尚未确认分析时的预留产品政策；不能把这一正常等待等同技术失败。跨 Case 缓存来源、编辑/批准/导出/分享、首次服务及真实环境验收继续在后续计划内完成。
