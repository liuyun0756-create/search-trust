# P5-03 第四批：独立 SEO 决定版本

日期：2026-10-27（Asia/Shanghai）

状态：用户已确认「证据快照不变＋独立决定版本」及本批只做底层保存、读取和验证的范围。本文待用户复核；尚未实施。

## 1. 目标与范围

在已保存的复核证据快照上记录 SEO 的下一阶段工作判断。每次保存形成不可变决定版本，可以读取、查询历史及恢复响应丢失的请求；不修改证据、原报告、批准交付或实施记录。

本批闭环：**读取固定证据 → 校验 SEO 输入 → 原子保存决定版本 → 读回/历史/同请求恢复**。

本批不做 UI、浏览器 BFF、公开或内部 HTTP 新入口、收费生成、模型或队列调用、重新采集、分享、PDF、生产迁移、部署或实际环境开关变更。新的底层服务不挂接现有工作区路由。现有 review 生成阻断全部保留。

保存决定免费，不等于生成报告、批准客户交付、客户认可或效果证明。既有商业规则不变：完整交付但没有足够行动依据的诊断报告消耗 1 点且不返还。本批不会触发该收费流程。

## 2. 方案选择与依据

采用独立决定版本，拒绝以下替代方案：

- 将决定写回证据快照：会破坏不可变历史，以及保存时已核对的校验值。
- 决定与新版报告生成一次接通：将免费记录、生成消费和交付揉在一起，超出本批范围。

已经核查的实现：

- `SearchTrust-RD/app/report_v22/review_evidence_models.py` 已定义 continue/adjust/observe/defer/new。
- `review_evidence_validation.py` 已校验行动身份、引用范围、实施前提和非暂缓项最多三项。
- `review_freeze_models.py` 的持久化快照要求 decisions 为空；本批继续保留。
- 旧投影模型要求决定时间不晚于 evidence evaluated_at。它适用于一次性组成的内存依据包，不适用于保存后再记录决定。
- `review_workspace.py` 目前只展示事实，保存后显示尚未记录决定；本批不修改该界面。

没有新增视觉布局决策，不使用视觉伴随工具。

## 3. 两个时间轴，两个独立对象

### 3.1 原证据快照

沿用 `SavedReviewEvidence` 和现有存储。其 review ID、bundle checksum、evidence checksum、evaluated_at、frozen_at 和所有来源保持原值；decisions 继续为空。

证据在冻结时的状态不因为后来经过更多天数而升级。例如旧窗口当时未结束，记录决定时依然不能把该快照解释成已满足窗口。

### 3.2 新决定版本

新增独立契约 `v22_review_decision_revision_v1`，包含：

| 字段 | 含义 |
| --- | --- |
| id | 一次保存的 UUID，同时作为幂等请求 ID |
| user_id / case_id / report_id | 由可信调用上下文绑定，不能由未来浏览器输入决定 |
| review_id | 精确关联既有证据快照 |
| evidence_checksum / bundle_checksum | 同时绑定证据核心和原完整依据包 |
| revision | 同一证据快照下从 1 开始连续递增 |
| previous_id / previous_checksum | 首版均为空；后续精确指向该快照的上一决定版本 |
| recorded_at | 数据库写入时产生的 UTC 时间，不能由调用输入指定或回填 |
| decisions | 本版本完整决定列表，不是补丁 |
| request_checksum | 对规范化业务请求的校验值，不包含数据库生成的时间和版本号 |
| checksum | 对完整已保存内容（除本字段外）的校验值 |

同一批决定统一使用版本的 recorded_at，不在各决定项内重复保存可冲突的时间或证据校验值。每条决定的来源固定为 SEO 记录。

recorded_at 必须不早于原快照的 evaluated_at 和 frozen_at。数据库时间异常早于这些值时拒绝写入，不能改旧时间或伪造新时间。后续重试已成功请求返回原时间。

不为了兼容旧投影而修改 evaluated_at、重新冻结证据、回填较早的决定时间或放宽旧 v1 验证器。新对象独立解析，旧纯投影及旧数据仍原样验证。

## 4. 决定内容与规则

所有输入为普通文本，不执行 HTML。沿用既有文本上限：理由/完成说明/重考虑条件各 1,200 字符，目标 2,000 字符，工作内容 4,000 字符；拒绝纯空白和不支持的控制字符。

| 类型 | 必填 | 不得推导的含义 |
| --- | --- | --- |
| continue／继续 | 原行动 ID、理由 | 不是系统证明原行动有效 |
| adjust／调整 | 原行动 ID、理由、目标、工作内容、至少一个合法引用 | 不是自动批准的新交付计划 |
| observe／完成后观察 | 原行动 ID、理由、SEO 完成说明；快照中存在该行动实施记录 | 不代表系统验收完成或效果成立 |
| defer／暂缓 | 原行动 ID、理由、重新考虑条件 | 不代表该工作无价值 |
| new／新增 | 不与原行动或本版本其他项重复的新 ID、理由、目标、工作内容、至少一个合法引用 | 不是系统自动发现的机会 |

非调整/新增不得带目标与工作内容；只有 observe 可带完成说明；只有 defer 可带重新考虑条件。未知类型、字段及非法字段组合拒绝。

每个原行动最多一个决定；原行动保持原 ID。没有决定的原行动显示为待决定，不默认继续，也不占用已确定项额度。允许保存部分决定或空列表，空列表表示没有已记录决定，不补造行动。新增项最多三条；非 defer 的全部决定（含 observe）合计最多三条，决定列表最多六条。超额明确拒绝，不截断、不自动替换优先级。

每项最多 12 个不重复来源引用。既有行动只引用该行动快照内的实施、页面、GSC、GA4 来源；新增项可引用该快照已有来源的并集。不得混入另一个快照或行动的来源；无可引用依据时不能保存调整/新增。零行动快照没有这些行动来源时仍可保存空决定版本，不借此新增无依据工作。

引用有效只证明可追溯，不证明理由正确。自由文本不转为系统结论，不自动进入客户报告。本批 read 仅供所有者内部使用。

## 5. 服务边界与规范化

新增后端小模块：`review_decision_models.py`（严格契约）、`review_decision_validation.py`（绑定与规则）、`review_decision_storage.py`（授权 RPC 与传输）、`review_decision_service.py`（保存/读回/历史流程）。SQL 迁移仍放在前端仓库的 `supabase/migrations/`。

语义规则可从旧验证器提取为共同纯函数，但必须保留旧时间检查、旧输入语义及全部回归测试。不能让新契约依赖拼装一份伪造的新证据 bundle。

保存请求只有请求 ID、可信上下文、review ID、预期上一版引用及决定项；不接受完整 bundle、证据数值、浏览器提供的可信用户身份、recorded_at、revision 或声明的校验通过状态。

服务读取精确快照，验证归属、报告绑定和全部决定。规范化时原行动按批准计划顺序排列，新增项保留提交顺序，引用排序；不改写文本内容。数据库重查同样规则，计算/验证规范化请求校验值。

输入正文和决定内容统一限制为 64 KiB（UTF-8），字符数限制不能替代字节数限制。JSON 重复键、未知字段、非有限数值、非法 UUID 和超限输入必须拒绝。不能因输入超大而截断后保存。

## 6. 原子保存与并发

每个快照维护一条线性决定历史，不跨快照续写版本。

1. 校验请求结构，并重新验证当前用户拥有 active Case、路径报告与快照匹配。
2. 先按请求 ID 检查已有记录。同用户、同上下文、同规范化请求返回原回执；同 ID 不同内容返回 CONFLICT。不得泄露其他用户的 ID 是否存在。
3. 首次保存事务锁定 Case 及对应证据行，重查权限和快照身份；锁定证据不改变其内容。采用与既有存储一致的锁顺序，避免并发归档/转移穿透授权。
4. 读取该快照当前决定头。首版要求 previous 为空且不存在历史；后续要求 previous ID/checksum 等于当前头。不一致返回 STALE，不能覆盖别人刚保存的版本。
5. 数据库校验类型、行动/来源绑定、数量、字段、大小和文本约束；产生时间与下一个 revision，写入一次并返回。
6. 已成功同 ID 重试优先于当前头判断，因此后来已有新版本也能恢复旧请求；但每次恢复仍重查所有权与 active Case。

不同 ID、同一 previous 的并发请求仅一个成功，另一个得到 STALE。同 ID、同内容并发返回同一结果；同 ID 异内容不覆盖。相同业务内容使用新 ID 且正确上一版可保存新版本，表示一次新的明确记录，但仅时间/版本号变化不能被以后解释成工作决定变化。

版本一经保存不可 UPDATE/DELETE。修改、移除一个决定或清空决定通过提交新的完整版本表达；历史保留。切换证据必须建立该快照自己的首版，不能自动复制旧决定。

## 7. 读取、历史与失败恢复

内部接口：

- `save`：明确引用快照和上一决定版本，返回完整已保存版本。
- `read`：按精确决定 ID 读取并校验 owner/Case/report/review 绑定；不存在或无权限采用统一不可用错误。
- `history`：按明确 review ID 列出该快照的决定元信息，revision 倒序，每页最多 20 条，游标为上一页最后 revision；每页重新授权。

历史目录仅含 ID、revision、previous ID、recorded_at、checksum、决定数量，不把私人理由放入目录。无历史是空列表，不等同于读取失败。返回内容严格校验、验证校验值与版本上下文，不能直接信任存储响应。决定读取/保存回执的响应上限为 128 KiB，历史目录上限为 32 KiB；数据库首次写入前检查完整回执大小，不能写入后才将超限当作未保存。内部读取原证据继续沿用既有证据传输上限，不将完整证据塞入决定回执。

保存超时或响应丢失属于结果未知。调用者保留原请求 ID 和原请求，通过 read 或同 ID save 恢复；不能自动另发新 ID。格式不合法的成功响应也不能断言写入回滚。

| 错误 | 语义 |
| --- | --- |
| INVALID | 内容、字段或证据绑定不合法 |
| UNAVAILABLE | 记录不可用、权限不足或 Case 不活跃，不泄露他人记录存在性 |
| CONFLICT | 同请求 ID 已绑定不同内容 |
| STALE | 所基于的上一决定版本已不是当前头，或首次保存时间条件不成立 |
| TOO_LARGE | 请求或结果超过支持大小 |
| STORAGE_UNAVAILABLE | 暂时存储/传输失败，不能显示为空历史或保存成功 |

采用明确的 `V22_REVIEW_DECISION_*` 错误命名空间，不返回 SQL/供应商原始错误或私人内容。传输沿用可信配置、固定 HTTPS RPC、禁重定向、有界读取和 30 秒超时。

## 8. 数据权限与集成隔离

新表启用 RLS，撤销 public/anon/authenticated/service_role 的直接表权限，仅 service_role 可执行受限 SECURITY DEFINER RPC；固定 search_path。所有 RPC 均验证 owner、active Case、报告与快照链，不以 ID/checksum 代替权限。

现有证据表、报告表、实施表和账本不写入；新表只通过外键和校验值关联证据。已保存证据的读取不重新拉取 Google 数据，不依赖目前采集开关。证据内任何受限状态都保留原义。

本批没有服务注册到线上路由，因此不新增或开启运行开关。原工作区 schema、导出契约和“尚未记录决定”文案保持不变：决定 UI 是后续单独接入项，不能把本批完成宣称为用户可用的完整功能。
