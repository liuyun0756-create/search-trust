# P3 首次服务竞品发现后台接线

继续已批准首次服务设计。本批只连接首个发现任务和后台恢复；不增加收费、不开放 UI/API，补充和过期刷新继续下一批。

## 执行方案

数据库中的已付发现请求是恢复来源。后台按有限批次扫描，首次提交先登记一次性派发标记；未知 SQL 响应不会另建任务。如果 Redis 状态曾丢失，不能判断采集/成本是否已发生，因此不重建该任务或重置成本，等待原技术期限结算。已存在但尚未运行的队列任务可以重新入队。

首次服务使用独立 Redis 命名空间及队列函数，复用真实竞品发现服务与共享市场缓存，不让旧 Prospect 恢复器绕过服务点数/截止时间检查。每次执行获取 SQL 租约，固定原任务 ID、请求、期限及最多三次执行；心跳失去租约或原期限届满立即取消。准备期仍使用原已扣的一点。

后台结果登记前核验请求摘要、Case、发现 ID、输入摘要及市场快照引用；只从后台持久任务读取成功/失败，不接收浏览器自报结果。未知网络状态不退款；明确失败及原技术期限超时使用上一批原子结算 RPC。成功登记后停止扫描，不把等待人工确认当成超时。

定时恢复会在后台启动/重启后继续，开关默认关闭且依赖能力生成及采集配置。队列函数在没有配置时不访问来源。首次服务正式采集使用同一独立发现仓储验证候选；获客流程保持原仓储不变。

## 验证与交付边界

SQL：派发一次、租约互斥/续期/接管/旧令牌、原期限、次数上限、来源权限、完成/补偿后禁跑、浏览器角色撤权。后端：真实 Redis 仓储（本地 FakeRedis）、真实竞品发现 worker 与受控来源，模拟队列丢响应、状态丢失、SQL 不确定结果、结果身份错配、失败退款、心跳取消、默认关闭；外部供应商不实际请求。

不得将本批称为完整首次服务上线。原生 Redis/PostgreSQL 并发、真实供应商和登录环境、人工补充/刷新、页面开始确认与端到端验收仍保留。
