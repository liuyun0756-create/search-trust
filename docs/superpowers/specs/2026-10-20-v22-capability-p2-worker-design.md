# P2 接续：冻结来源到实际任务执行器

执行已批准主计划 §1、§4、§6–7 和 D1；不新增商业决定、不部署、不启用生产或收费入口。

## 现状与约束

旧 worker 只解析两种旧 envelope，Redis 成功载荷只接受 ReportV22。2.2.2 的规则、检查点、结算和完成权益读取已有，但仅输入摘要不足以恢复 queries、业务身份、共享搜索上下文和规则限额。旧公开快照保存与旧报告落库耦合，不能为新版生成虚构旧报告。

采用独立、默认关闭的新版执行分支，不让旧任务隐式换格式。请求只含 Case/manifest ID、冻结摘要、报告类型，不接受客户端传来源正文。新 worker 通过仅服务端 RPC 读取准确的冻结输入，走已实现公开/服务规则和结算适配器。

## 输入准备与恢复

- 新原子 prepare RPC：在已预留的一点任务下保存四种公开快照、调用原 freeze 校验、保存去来源正文的生成 recipe。GSC/GA4/可选官方 GBP 使用已有授权快照，不能由本次请求插入私有数据。
- recipe 保留规则配置、业务上下文、source binding 和共享搜索元信息；不复制公开 payload、私有 normalized_payload 或官方 GBP 临时 raw_payload。SQL 用固定 manifest 引用的数据快照还原完整输入，再与本次完整 canonical 字节和 generation_input_checksum 校验。
- resolve 严格核对任务代次、冻结 manifest 摘要、Case、收费及来源健康/匹配/授权/有效期。只有原冻结快照，不读取最新替代来源。
- 已结算成功时直接恢复不可变完整报告，不依赖原来源仍有效，不重跑生成、不再收费。失败/已返还不复活。
- 活动任务必须同代；较早代次已经提交的完整报告可在后续接管代次恢复。超时/耗尽重试前通过 SQL 终态裁决：成功恢复报告，否则原子确认技术失败/补偿；无法确定数据库结果时保持非终态，交给原任务重试/巡检，不凭超时推断返钱或交付失败。
- 官方 GBP 原始数据只在现有保留期内由原表暂时读取，recipe/checkpoint/Redis 报告不复制其原始内容；过期或已清理则拒绝活动分析。

## 执行、状态与兼容

新增严格 versioned envelope 和有界 RPC resolver。后台路由在独立开关及必需存储/回调配置就绪后才注入 capability executor；开关默认 false，未知 schema 继续拒绝，旧分支原样保留。

Redis 内部状态允许旧、新报告，但新报告须绑定自己的 job/Case。轮询/SSE 对新版成功只暴露明确版本的报告引用，不暴露 manifest、私有来源或完整 SEO 报告；旧 TaskStatusResponse 契约不改，额外响应模型另出 schema。内部新版请求不新增公共提交 API。

配套 recipe 保留私有来源的无正文 header，包括标准化时间精度及来源顺序，SQL 核对后补入实际快照正文。不能用 manifest 的等价时间字符串或重新排序的来源替代原规范化输入；这会改变完整生成摘要。报告交付的校验值采用双端统一数字规范化，历史快照与内部检查点摘要算法不变。

本批不建设首次服务收费入口，不启用开关。新 intake 之后应调用 prepare，再注册准确 envelope/排队；不能把本批默认关闭的 worker 当作用户已可使用的整链路。

## 验证

隔离 SQL 检查来源准备/recipe 原子性、摘要/跨用户/绑定拒绝、权限、不可变、撤销/过期、成功恢复；后端实际 worker+fakeredis+MockTransport 检查公开0–3行动、首次/有历史服务、响应丢失恢复、代次及旧任务兼容。全量快速测试、双端 schema/fixture 校验、类型与构建均需重跑。原生多连接 PostgreSQL、真实授权、部署验收不提前宣称通过。
