日期：2026-10-21。承接内部准备队列，把已有业务/竞品确认后的“开始分析”接到默认关闭的新路线。未部署、未启用，P2 整阶段仍未完成。

## 本轮实现

1. 保留原扣点时机：竞品发现开始时预留一点，分析开始不再次扣点。新增事务同时保存业务确认版本、绑定原预留工作流、创建原分析任务及不可变准备标记；事务失败不留下半成品。
2. 先验证用户、Case、工作流和 discovery 关联。首次登记再验证发现结果及竞品选择；重放先读取数据库中的原请求，不要求 Redis discovery 仍存在。请求、任务、工作流或前一任务不一致时拒绝。
3. 数据库提交响应丢失、准备排队前失败、排队后响应丢失都可以按原 job/generation 重试，不增加扣点、不切回旧生成链。已完成/失败任务只返回状态，不重新入队。
4. 前端提交分支传递服务端认证用户身份，跳过旧的单独 bind。服务未配置或契约不合法时安全失败，不自动降级到旧链。
5. 准备任务状态从数据库读取并校验；排队、采集、生成、失败只展示安全文本，成功只返回新版报告引用。SSE 提供命名为 `state` 的一次状态快照，后续沿用已有十秒轮询；不是新增持续数据库订阅。
6. 最新任务恢复仍使用原 Case 任务查询，最终完成引用引导已有新版报告页。未把新版报告 ID 填入旧报告字段；Case 报告列表索引尚未接入。
7. 正常完成的零行动诊断仍消费一点、不退款。原截止时间技术失败补偿保持一次；未确认分析、仍停留在竞品发现的预留不被误判为技术失败。

## 默认关闭与发布边界

- FE 新分支要求 `V22_CAPABILITY_DISPATCH_ENABLED=true` 且 `V22_CAPABILITY_INTAKE_ENABLED=true`；否则维持旧提交路线。原公开入口开关继续由路由包装器控制。
- BE 内部入口要求内部认证、`V22_ANALYZE_ENABLED`、既有 capability readiness 和新增 `V22_CAPABILITY_INTAKE_ENABLED=true`。配置默认 false。
- 本地实际开关：FE dispatch=false、intake=false；BE capability execution=false、intake=false。未修改环境秘密、远程配置或数据库。
- intake 开关控制接收新工作；不要在已有任务执行中同时停掉执行/截止时间恢复。发布仍须制定排空、恢复及回滚策略。
- 竞品发现已经预留额度，但尚未点击确认分析，是原产品工作流的等待窗口；本轮没有变更其计费政策或宣称该窗口已全部消除。
