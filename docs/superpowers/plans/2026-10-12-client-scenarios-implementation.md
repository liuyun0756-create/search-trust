- 两个小型产出预览：`Before you win the work` 展示“观察 / 客户问题 / 初步方向”；`Once the work begins` 展示“建议 / 执行步骤 / 复核依据”。

删除原来围绕首屏漂浮的抽象问答卡。产出预览使用可阅读的材料节选，不放假增长数字、客户头像或“资深 SEO 推荐”背书。

## 3. 完整故事卡如何展示

### 3.1 每张卡的固定信息顺序

1. **处境标题**：像 SEO 当天真的会遇到的一件事，而不是功能名。
2. **故事**：人物工作背景、触发事件、眼前任务，2–3 句。
3. **卡点**：为什么不能照常发一张审计表或再做一次通用分析，1 句。
4. **SearchTrust 的介入**：产品如何整理支持的证据与建议，1–2 句。
5. **拿到的材料**：3–4 行具体内容，能看出这份材料如何被使用。
6. **SEO 的下一步**：拿材料去开会、定范围、交任务或调整计划，1–2 句。
7. **必要条件/限制**：贴近相关结论，不能只藏在全页底部。
8. **入口**：一个工作入口、一个完整样例链接；需要时再放轻量方法链接。

英文每卡以约 180–260 词为编写目标，不用字数限制裁切内容。标题尽量不超过两行；故事不写长篇人物传记。材料节选必须保留实际判断、对象或待核实信息，不能用“insight / action / result”三个空标签代替内容。

### 3.2 视觉排版

- 桌面：一张宽卡；左侧约 44% 是故事，右侧约 56% 是材料节选。
- 右侧像一份真正可读的工作材料，不像截图缩略图；文字可选择、可缩放。
- 底部“下一步”说明与入口完整展示，用户不用打开弹窗或进入另一个页面才能看完故事。
- 获客/服务可用浅绿/浅青背景区分，但不能只靠颜色识别阶段。
- 延续当前字体和深绿视觉，不另建全站设计系统。
- 内容区最大宽度沿用约 1200px；基础正文目标 16px，辅助文字不为塞内容缩到难读。
- 阴影和边框用于区分故事与材料；不增加持续动画、假仪表盘或装饰性数据图。

### 3.3 五种材料样式

| 样式 | 适用故事 | 展示方式 |
| --- | --- | --- |
| 对话简报 | A1、A3、B3 | 发现 → 意义 → 待问问题/验证条件 |
| 对照说明 | A2、D2 | 并列证据或检查方向；明确“观察”与“解释”不同 |
| 计划/执行清单 | B1、B2、C2、C3、D3 | 对象、行动、输入、完成标准；不做虚假的可编辑控制 |
| 判断修订 | C1、D1、E2 | 之前的判断 → 新信息 → 当前建议 |
| 客户复盘 | E1、E3 | 已确认工作、观察、未确认事项、下一阶段 |

这些是同一个故事组件的展示变体，不是五套完全独立的组件，也不是新增产品功能。除 C1 与现有样例衔接外，故事采用不同业务处境，避免全部复制同一份维修页面材料。

## 4. 十五个故事的内容执行清单

以下全部是**模拟工作场景**。人物、业务处境和材料节选用于解释用法，不作为已验证客户案例或实际业绩。卡片材料统一带 `Illustrative workflow excerpt`；场景区说明 `Fictional situations, not customer testimonials. Excerpts show how an SEO can use the reports—not additional report products.`

### A 组：找到值得开始的对话

#### A1｜明天第一次聊，对方只给了一个网址

- ID：`first-conversation`，保留现有深链接。
- 英文标题：`Tomorrow’s first call. All you have is a website.`
- 故事：一位独立 SEO 收到朋友转介绍，对方是一家本地牙科诊所。明天见面，现在只有官网，没有 GSC、GA4 或业务后台权限，也不适合先投入半天做免费完整审计。
- 卡点：泛泛说“网站需要优化”无法建立专业判断；现在也不能假装知道客户流量和咨询问题。
- 产品介入：把可用的站点、公开商家与已确认竞品证据整理成初步发现及待确认问题。
- 材料节选「首次沟通简报」：①已检查页面对急诊服务时段和预约入口交代不清；②这使服务信息值得核实，但不证明因此丢失咨询；③问客户该服务是否为当前重点、实际由哪个页面承接；④初步方向是确认目标页面后再讨论信息与联系路径。
- SEO 拿到什么：有依据的开场材料和提问顺序；可以带着具体观察沟通，不承诺诊断已经完整。
- 入口：P0 + SP；可补 M01。

#### A2｜客户说：为什么隔壁那家总排在我们前面？

- ID：`competitor-question`。
- 英文标题：`“Why does that competitor keep showing up above us?”`
- 故事：本地水管服务商发来一次搜索截图，希望 SEO 直接解释对方为什么排名更高。截图只代表一个查询和位置，不能直接当作完整竞争结论。
- 卡点：指出对方“有某个页面/评论更多”不等于找到了排名原因。
- 产品介入：基于已确认的服务、区域、竞品及可用公开证据整理差异；查询位置与业务相关性需要 SEO 核实。
- 材料节选「竞争观察」：①双方是否确实覆盖同一服务与区域；②对方页面明确展示服务范围与联系路径，本方已检查页面相关信息不足；③优先检查本方是否有另一承接页面；④将观察作为调查方向，不标记为“排名差距的原因”。
- SEO 拿到什么：可以解释的竞争差异和检查方向，而不是未经证明的排名承诺。
- 入口：P0 + SPE；M01。

#### A3｜对方已经收到了三份免费审计

- ID：`beyond-free-audits`。
- 英文标题：`They already have three free audits.`
- 故事：一家景观维护企业已拿到几份长审计 PDF，里面都是错误数量和评分。对方问的是：“你会先解决什么，为什么？”
- 卡点：再发更长的错误清单，只会进入同质化比价。
- 产品介入：把有证据支持、与目标服务相关的问题和行动建议放在一起，供 SEO 筛选重点。
- 材料节选「重点诊断」：①季节性维护服务的覆盖、适用客户和询价条件分散；②与当前想推广的服务相关，值得作为沟通重点；③先确认现有服务页面，再补明确的信息；④保留后台数据和业务优先级尚未确认的说明。
- SEO 拿到什么：一份讲得清“问题—意义—初步行动”的简报，用专业判断区分服务，而不是比较审计条目数量。
- 入口：P0 + SPA；M05。

### B 组：把兴趣变成明确的工作范围

#### B1｜预算有限，这个月到底先做什么？

- ID：`limited-budget`。
- 英文标题：`A limited budget. A longer list of possible work.`
- 故事：潜在客户愿意合作，但第一阶段只有有限预算。站点内容、联系路径、商家信息都有人提过意见，SEO 需要给出一个可解释的起点。
- 卡点：不能把所有建议都叫“高优先级”，也不能用未经支持的收入预测排序。
- 产品介入：给出有证据的行动起点和相关限制，SEO 再结合业务目标、影响方向、依赖与可用资源调整已有行动。
- 材料节选「首阶段安排」：①先确认与重点服务有关的页面和联系信息；②优先处理证据明确、能推进目标服务且当前可执行的事项；③依赖开发和业务确认的工作暂缓；④写明暂缓原因和重新评估条件。
- SEO 拿到什么：能向客户解释的首阶段工作安排；排序是专业判断，不宣称系统算出了商业价值分数。
- 入口：P1 + SPA；M05。

#### B2｜“帮我们做 SEO”不能直接成为工作范围

- ID：`first-scope`，保留现有深链接。
- 英文标题：`“Handle our SEO” is not a usable scope.`
- 故事：客户默认内容、开发、商家资料、追踪设置都在报价里；SEO 原本只准备处理一组核心页面。双方还没说清楚谁负责提供信息、谁负责上线。
- 卡点：范围不清会让后续工作不断扩张，也难以解释什么算完成。
- 产品介入：利用报告中的行动对象、步骤、完成标准和可编辑工作字段，准备范围讨论材料。
- 材料节选「范围确认清单」：①本阶段要处理的服务页面与内容；②客户确认的服务范围、资质和联系方式；③谁提供素材、谁实施、谁审核；④完成标准与后续观察方式。合同外事项由 SEO 在自己的合作文件中列明。
- SEO 拿到什么：用于报价和合作沟通的工作基础；不是系统自动生成合同、报价或无限任务管理。
- 入口：P1 + SPA；M05。

#### B3｜客户问：多久能排上去，能保证吗？

- ID：`set-expectations`。
- 英文标题：`“How soon will this work—and can you guarantee it?”`
- 故事：接近签约时，客户希望得到明确结果日期。SEO 需要既解释投入价值，又不把计划写成排名保证。
- 卡点：工作完成时间和搜索表现变化不是同一个承诺。
- 产品介入：以具体行动、完成检查和数据复核建议支撑阶段目标说明。
- 材料节选「阶段目标与验证」：①承诺可控的工作对象与完成标准；②待观察的是相关搜索活动和经过确认的联系事件；③观察条件包括可比时间段、数据质量和样本；④数据不足时保留判断，复核日期由 SEO 与客户协商。
- SEO 拿到什么：能解释“我们会做什么、如何观察、什么不能保证”的材料。
- 入口：P0 + SPA；M06。

### C 组：把判断变成可以执行的工作

#### C1｜拿到客户数据后，原来的建议需要改了

- ID：`revisit-recommendation`，保留现有深链接。
- 英文标题：`Client access changes the first recommendation.`
- 故事：获客阶段曾怀疑需要新增空调维修页面。客户接入后确认已有承接页面，可用搜索数据也显示它获得了相关搜索活动。
- 卡点：继续照最初提案新建页面，可能重复已有内容；新证据必须有机会改变结论。
- 产品介入：把客户确认和支持的数据证据加入判断，形成修订建议。
- 材料节选「判断修订」：①原先待确认：是否缺少服务承接页面；②新信息：已有页面及相关搜索活动；③当前建议：优先改善已确认页面的信息和联系路径；④仍需核实：事件含义、业务优先级和其他潜在限制。
- SEO 拿到什么：有修订理由的行动计划，可以向客户说明为什么改，而不是把旧建议包装得更肯定。
- 入口：S0 + SV；M02。

#### C2｜知道该做什么，还需要一份别人能执行的说明

- ID：`execution-brief`。
- 英文标题：`A recommendation still needs an execution brief.`
- 故事：SEO 已决定改善一家清洁公司的服务页面，但文案或开发需要知道改哪里、客户要提供什么、怎样才算完成。
- 卡点：“优化服务页”不足以交接工作。
- 产品介入：用行动计划中的目标、步骤、完成标准等内容准备执行说明，SEO 审阅并调整工作字段。
- 材料节选「执行说明」：①对象：已确认的商业清洁服务页面；②步骤：补充经客户确认的服务范围、适用情况与联系入口；③输入：服务事实、区域、限制与客户批准；④完成检查：信息一致、入口可用、页面表达符合确认范围。
- SEO 拿到什么：可交给执行者的任务基础，减少从空白整理说明的工作。
- 边界：不展示“自动生成并保存完整文案”“一键发布”或系统已记录实施完成。
- 入口：S1 + SVA；M05。

#### C3｜开发排不上，客户资料也没给齐

- ID：`blocked-dependencies`。
- 英文标题：`The developer is booked. The client inputs are late.`
- 故事：原计划的第一项需要模板修改和客户资料，但开发本月没有空档；SEO 仍需要推进有意义、可执行的工作。
- 卡点：技术上合理的排序，不一定符合这个客户当前的资源条件。
- 产品介入：SEO 使用可编辑行动计划调整顺序、步骤、负责人和时间安排；原始证据不被改写。
- 材料节选「调整后的工作安排」：①将不依赖模板修改且证据明确的行动前移；②保留被阻塞行动及待提供输入；③写明负责人和恢复条件；④调整目标范围时保留它尚需核实的说明。
- SEO 拿到什么：能继续推进的现实计划；不是自动催办、开发排期或依赖管理系统。
- 入口：S1 + SVA；M05。

### D 组：数据变化后，重新制定重点

#### D1｜核心页面点击下降，是否要打断原计划？

- ID：`clicks-declined`。
- 英文标题：`Clicks fell on a key page. Should the plan change?`
- 故事：例行复核时，SEO 发现一个重点页面在所选可比范围内的点击下降。客户希望马上推翻原计划，但变化原因还不清楚。

- 边界：这是用户发起的复核场景，不是实时监控、主动预警，也不是自动归因。

- SEO 拿到什么：从“流量上涨”转向“业务相关性与联系路径”的调查安排。
- 边界：不自动读取 CRM，不把事件标成有效客户或证明页面问题导致咨询不足。

#### D3｜第一轮工作结束，下阶段不能只是再跑一遍审计

- 产品介入：用最新支持的分析与行动建议作为新起点，SEO 对照自己确认的实施记录和客户目标调整计划。
- 材料节选「下一阶段建议」：①继续：证据仍支持且未完成的重点；②暂缓：前提未满足或当前不重要的事项；③新增/调整：确有新证据支持的方向；④保持观察：没有足够变化时不制造新问题。

## 6. Tab 与横向卡片的精确交互

### 6.1 选择与记忆

- 阶段层：两个 Tab；分组层：获客两个、服务三个 Tab。
- 每个阶段记住最后访问的分组；每个分组记住最后访问的卡片。
- 首次进入一个分组显示第一张；再次回来恢复上次卡片。
- 只在当前页面组件内记忆，不新增 localStorage、账户偏好或服务端保存。
- 刷新时以 URL 中的有效故事 ID 恢复；没有 ID 回到默认。
- 点击分组、故事标题或箭头不强制将整页滚回顶部。
- 三个故事短标题始终可见，不以三个无名称圆点代替；当前故事用边框、文字和选中状态区分。

### 6.2 滑动

- 一次阅读一张宽卡，露出下一张卡的少量边缘提示可滑动。
- 桌面宽度目标：当前卡约占可用轨道宽度 92%–95%，间距约 20–24px；按实际容器微调。
- 小屏目标：当前卡占约 94%，间距约 12px；优先保证卡片正文宽度，不为露边牺牲阅读。
- 支持触屏横滑、触控板、前后箭头及故事标题按钮。
- 不自动播放、不无限循环、不拖拽抢占文字选择；第一张禁用上一张，最后一张禁用下一张。
- 滑动结束后对齐当前卡起点；最后一张通过轨道尾部留白确保也能正确对齐。
- 计数为当前组 `01 / 03`，不是旧页面写死的 `/ 04`。
- 原生纵向页面滚动必须保持可用；不使用会阻止纵向手势的设置。

### 6.3 不折叠、不截断的含义

- 卡片内容全部展开，没有 Read more、折叠箭头、展开详情弹窗。
- 内容长时正常增加页面高度；用户纵向滚页面阅读。
- 卡内没有第二个纵向滚动区，不使用固定高度加隐藏溢出或 line-clamp。
- 同组卡片通过轨道自然等高保持滑动时稳定；允许卡底部少量留白。
- 不把所有五组强制拉到全页最长卡高度。切组时允许自然高度调整，文案长度保持接近以降低跳动。
- 手机内部上下布局：故事在上、材料在下、结果和 CTA 在后；仍然是横滑切换下一故事。

### 6.4 定位、深链接和边界

- 统一故事地址 `#practice-{id}`；直接访问任意一个 ID 都能显示对应卡。
- 保留 `first-conversation`、`first-scope`、`revisit-recommendation`、`next-priorities`。
- 保留当前 `scene-01` → `first-conversation`；`scene-02/03/04` → `revisit-recommendation`；`scene-05/06` → `next-priorities` 的旧别名。
- 用户主动切换时用 replaceState 同步当前 ID，避免浏览器返回要经过十五次卡片操作；保留 URL 原有查询参数和 history state。
- 初次有效深链接或外部 hash 导航可将场景区定位到视口，预留页头距离；普通组内切换不触发页面纵向定位。
- 监听外部 hash/history 变化恢复选中；未知 ID 安全回默认，不报错或产生空白面板。
- 页面缩放、字体加载、容器尺寸改变后重新定位当前卡；当前索引不能漂移。
- 连续快速点下一张、平滑滚动中触摸打断，以最终可见位置为准；不能旧回调覆盖新选择。

### 6.5 实现中必须修正的旧逻辑

- 现有 `viewport.clientWidth * index` 不适合新增的卡片露边和间距。改为测量卡片相对轨道的实际起点，滚动同步选择最近起点。
- 不依赖固定“相差 3px”来识别完成；处理小数尺寸、缩放和末尾最大滚动距离。
- 现有面向两个选项的左右键逻辑不能直接套在三个分组上；左键减一、右键加一，按实际数量循环。
- 使用 ResizeObserver 或等效尺寸同步机制；清理监听、定时器和观察器。
- 内容数据不再通过固定维修报告的 actions.map 派生十五个故事；样例入口与故事内容分开维护。

## 7. 可访问性与状态

- 两层 Tab 各有独立 `tablist` 名称、对应 `tab/tabpanel`、`aria-selected` 和 roving tabindex。
- 左右键在当前 Tab 层切换，Home/End 到首尾；两层快捷键不能串到彼此。
- 故事标题选择器是普通按钮组，使用 `aria-current`，不再增加第三层 Tab 语义。
- 卡片区域有明确名称，当前卡读作“本组第 1 个，共 3 个”；切换后只简短宣读新标题和序号，不重复整张故事。
- 非当前卡可以视觉露出边缘，但其链接和按钮不能进入键盘焦点；用 inert 和相应可访问性状态处理。
- 点击箭头后焦点留在箭头；键盘切换分组后焦点留在对应 Tab。若当前聚焦控件即将因切换隐藏，应先将焦点移到稳定的故事选择控件，不能遗留在隐藏卡片中。
- 不拦截卡片正文中的方向键来强制翻页；用户可正常选字、阅读、操作链接。
- 箭头等点击区域至少 44×44px；焦点描边清晰，不被横向裁切。
- 支持 reduced motion：使用即时定位而非平滑滚动；不添加自动播放。
- 常态、hover、focus、选中、disabled 均可区分；禁用箭头不仅依赖颜色。
- 内容是本地静态数据，不新增加载骨架或假“正在分析”状态。无效数据在测试/构建阶段发现，未知锚点运行时回默认。
- 200% 缩放可读；320px 屏宽没有整页横向溢出；手机 Tab 可换行，文字不能被省略成无法辨认。

## 9. 内容真实性检查

每个故事发布前核对以下四类，不用大段免责声明削弱正文，但相关限制必须贴近对应材料：

| 类别 | 写法 |
| --- | --- |
| 当前产品能力 | 明确产品提供的证据、建议、行动字段和交付能力。 |
| SEO 的人工工作 | 写明客户事实、实施情况、业务优先级和沟通安排由 SEO 确认。 |
| 示例材料 | 标记为模拟用法，不冒充真实后台截图或实际客户结果。 |
| 不支持的能力 | 不写为已有功能；不靠“模拟”标签包住一套并不存在的产品工作流。 |

额外约束：

- 接入数据可能支持、修订或保留原判断，不保证“接入后所有问题都明确、优先级自动确定”。
- 影响程度可以谈与业务目标、排名/流量路径的关联和直接程度，不编造自动影响分数、预期流量或收入。
- GSC/GA4、公开 GBP 资料与官方 GBP 后台访问不混用；公共资料不是私有账户数据。
- 月度与季度复盘是报告材料的使用方式，不是新增第三种报告；只有 Prospect Evidence Report 与 Verified Action Plan 两种现有报告产物。
- 三项行动编辑器不暗示无限增删任务或完整项目管理能力。
- 无证据不能写“已改善”“已解决”；没有变化不为了展示价值制造变化标记。
- 不写“节约 80% 时间”“客户增长 30%”等没有测量依据的效果。
- B、C 组强调可执行材料，D、E 组强调依据与决策；不能十五张卡最后都只落在“你现在可以和客户沟通了”。

| `src/lib/seo.ts` | 只修改 useCases 条目。 |
| `src/components/useCase/UseCasesV22.test.tsx` | 替换四故事旧断言，增加新结构、边界和语义测试。 |
| `src/components/useCase/practice-scenarios.test.ts`（新增） | 数量、唯一 ID、分组归属、必填字段、入口与别名。 |
| `e2e/use-cases-workbench.spec.ts` | 五组十五卡、滚动、深链接、记忆、焦点和响应式。 |

`use-case-data.ts` 仍被 Method 使用，不因名称相近当旧代码删除；`UseCaseEvidenceVisuals.tsx` 也不顺带重写。只有确认关联链接不成立时才最小修改调用处并补测试。

### 数据结构要求

- `Stage`：id、label、description、groupIds。
- `Group`：id、stageId、tabLabel、title、description、scenarioIds。
- `Scenario`：id、groupId、shortTitle、title、story、tension、assistance、artifact、nextMove、boundary、primaryCta、sampleLink、可选 methodLink。
- `Artifact`：kind（五种之一）、label、title、3–4 个结构化内容项；按类型保留适合的列/步骤标题。
- 不在渲染组件内拼十五段文案；不要再隐式依赖同一份样例 actions 长度。
- 用 ID 查分组和阶段，单一关系源；所有数量从数据计算。

### 组件接口要求

| 组件 | 输入与责任 |
| --- | --- |
| ScenarioWorkbench | 接收 stages/groups/scenarios；默认首阶段首组首卡；持有 selectedStage、各阶段 selectedGroup、各组 activeIndex。 |
| ScenarioCarousel | items、activeIndex、onActiveIndexChange、可访问区域名称；接收明确的跳转目标；不自建第二套冲突状态。 |
| ScenarioStoryCard | scenario、isActive；只渲染内容、材料变体和链接；无分析/点数副作用。 |

不为了此次页面加入轮播依赖库或全局状态库；优先使用现有 React 和原生滚动能力。

## 11. 实施顺序与每步完成条件

### 第一步：锁定内容与能力对应

工作：按本计划写完十五个英文故事，填齐材料节选与入口；逐项核对实际能力；检查旧四个 ID 和 Method 链接。

交付：完整数据表、主次入口映射、能力边界清单。

完成条件：没有“稍后补充”的故事，没有十五张同质化材料，没有把人工工作写成自动能力。

### 第二步：先做一张卡和完整分组导航

工作：先实现 A1 的完整卡片和 C1 的判断修订变体；搭建两阶段/五分组导航及五类材料基础排版。

交付：桌面与手机可读的静态版面。

完成条件：故事、产品介入、材料和下一步一眼可区分；全部内容可读，无折叠和卡内纵滚。此处先检查视觉方向，再批量填充剩余故事，避免十五张一起返工。

### 第三步：实现滚动、状态与深链接

工作：实测卡片起点定位；完成按钮/触摸切换、组内记忆、直接链接、别名、快速操作和尺寸变化恢复。

交付：可以用鼠标、键盘、触屏浏览的五组三卡工作区。

完成条件：三种切换入口得到相同选中结果；卡片与序号、URL 不不同步；普通切换不把用户滚走。

### 第四步：填入十五个故事并完成整页

工作：完整内容、首屏、角色分工、底部入口、FAQ 和 metadata；核对 Sample Reports 与 Method 对应入口。

交付：完整 Client Scenarios 页面。

完成条件：从获客到长期服务的十五个切入点都能到达；服务期条件和模拟说明可见；浏览页面无分析副作用。

### 第五步：自动化与人工验收

工作：更新旧断言、新增数据测试、浏览器交互/响应式测试、关联营销入口回归、键盘和触摸检查。

交付：测试结果、关键视口截图、未通过项及修复记录。

完成条件：满足下节所有硬性验收；测试环境故障与功能失败分开报告，不能把没跑的项目写成通过。

### 第六步：审阅与发布准备

工作：交付本地预览及内容/功能差异摘要；用户可按五组检查卡片。若需上线，执行独立的发布核验与正式环境只读冒烟。

完成条件：内容和交互已审阅，构建通过，关联入口无回归。当前计划阶段不发布、不提交现有混合改动、不清理旧数据。

## 12. 测试与验收清单

### 内容与数据

- 两阶段、五分组、每组三个故事，总数十五；无重复 ID。
- 所有故事包含具体处境、介入、材料、下一步、必要边界。
- A1–B3 以获客/范围材料为主；C1–E3 明确服务前置条件。
- 十五张不是十五种新报告；模拟标签在桌面和手机均可见。
- FAQ/schema 同源；标题描述没有残留四场景文案。

### 交互

- 遍历五个分组、十五个卡片，每张标题及内容可见。
- 每组首次进入第一张，返回记住上一张；跨阶段保留各自分组。
- 箭头、标题按钮、横滑结果一致；首尾禁用正确，没有自动轮播。
- 连点、平滑滚动打断、缩放、横竖屏、窗口调整后无错位。
- 卡片不折叠、不截断、没有内部纵滚；页面本身可以正常纵向滚动。
- 控件切换不会强制滚页；卡片露边不造成整页横向滚动。

### 链接与可访问性

- 十五个新地址及四个原 ID 均恢复正确故事；六个旧别名无回归。
- 未知锚点安全处理；外部 hash 变化正确恢复；查询参数保留。
- 两层 Tab 的左右/Home/End 正确且隔离，尤其服务三个分组。
- 非当前卡不接收键盘焦点；切换后焦点可见，无焦点遗失。
- reduced motion、200% 缩放、屏幕阅读器简短切换提示通过人工检查。
- 所有样例和方法锚点实际存在，跨页进入后相应内容能读到。

### 视口与截图

- 320、390、768、1024、1440px 五档检查。
- 桌面重点截 A1、C1、D3；手机至少每组一张并检查最长卡 E3。
- 页面整宽、末张对齐、底部 CTA、两层导航换行、正文缩放都要检查。
- 真实触摸或触屏仿真测试横滑及纵向页面滚动；不能只用 scrollLeft 脚本替代手势验收。

### 副作用与关联回归

- Tab/滑动/故事导航不能发起分析、报告生成、支付、点数扣除或写业务数据。
- 不以“零任何网络请求”误伤正常静态资源；重点检查业务 mutation 请求。
- 首页、Method、Sample Reports、导航和现有工作入口回归。
- 不使用生产账号跑付费分析来验收静态营销页面。

## 13. 完成后的交付与维护

最终应交付：

1. 可预览的完整页面：两阶段、五组、十五张完整故事卡。
2. 独立数据文件，可按一个故事修改内容，不需要触碰滑动逻辑。
3. 测试与五档视口检查结果，明确本地验收和线上验收的区别。
4. 变更文件清单、能力边界、仍需产品支持的事项。

内容来源以本计划和 `practice-scenarios.ts` 为执行基准，能力边界对照 `docs/website-report-alignment-backlog.md`。实施者整理文案，产品负责人审阅业务表达；任何新增自动化承诺必须先核对真实产品支持。后续功能变化时同步复核故事、FAQ 和样例入口，不只更新宣传标题。

最终验收的核心：**一个独立 SEO 不需要先学完产品流程，就能找到自己的处境，看见具体材料，并知道如何用它推进下一步客户工作。**
