# P5 GA4 evidence audit and independent SEO review — local acceptance

Implements the approved no-permission-expansion scope in [the design](../specs/2026-10-23-p5-ga4-evidence-review-design.md). Brainstorming scope review kept the change inside that agreement; React and web-testing guidance informed on-demand loading, draft preservation, accessible controls and actual-component testing. The unavailable writing-plans skill was replaced with the execution checklist in the design. No new marketing promise.

## Delivered

- Exact collections now write `ga4_comparison_observation_v2`, with six bounded truncation checks: before/after × totals/dates/key events. Provider reason types and date boundaries are retained; free-text provider messages are not stored. Invalid truncation shapes fail the collection instead of being silently treated as unrestricted. Existing provider budget and read-only OAuth scope are unchanged.
- The original v1 observation serialization and qualification calculation remain reproducible. Ordinary `ga4_sync_v1` payloads are untouched. New observations use the `v22_ga4_qualification_truncation_v2` ruleset; relevant metrics receive a truncation reason but remain not comparable. SQL accepts both paired versions and still requires completeness/history restrictions, null effect conclusions and false causal attribution.
- A reproducible evidence audit is bound to the original observation checksum, collection, scope and windows. It lists absent dates without zero-filling; captures per-view sampling, thresholds, other-row loss, metric restrictions, empty-result flags, event-list truncation and provider truncation; and identifies added/removed/changed current key-event settings across collection. Event changes cover the already collected fields only: presence, counting method, creation time, custom and deletable. At most 30 differences are displayed, with the total count. Older observations explicitly show that provider truncation metadata was not captured.
- Independent SEO checks cover date-coverage investigation, historical event settings and measurement setup. Checked/uncertain states require a plain-text basis. Records are explicitly `seo_recorded`; no state named “system verified” exists. They cannot alter source evidence, qualification, reports, delivery revisions, implementation records, credit balances or comparison eligibility.
- Migration 67 adds append-only reviews, owner/report/delivery/source validation, revision CAS and durable request IDs. Same-ID replay returns the original receipt even after later revisions; changed requests conflict. Records carry actor, server timestamp, observation checksum and content checksum. The latest 20 revisions are returned; earlier records remain stored. Direct mutation is denied, including to the service role outside the authorized functions.
- Separate owner-authenticated BFF/internal API reuse the existing default-off GA4/comparison gates. Request identity is derived from the logged-in owner; writes require same origin. Body/response bounds, strict contracts, response integrity, safe errors and no-store behavior are retained. Reading/saving invokes no provider, queue or credit operation.
- The existing successful-collection panel now has an on-demand evidence/review entry. It distinguishes **system-observed evidence**, **SEO checks**, and **still unverified**. Closing/reopening the disclosure retains the draft. A lost save acknowledgement retries the same request; a conflict retains the draft until the latest saved revision is loaded. The last 20 revisions are inspectable. Pending save recovery is in-memory: the UI asks the user to keep the panel open; no claim of cross-navigation draft persistence is made.

## Evidence boundaries

All requested dates being present is not processing finality. Equal current settings at two collection instants do not establish full historical settings. “No issue found in my checks” is an SEO statement, not system attestation. There is no 48-hour completeness shortcut, no numerical comparison unlock and no uplift/causal conclusion.

Source specification checked: [Google Data API ResponseMetaData](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/ResponseMetaData), including dataTruncationReasons, typed reasons and inclusive date boundaries. Prior design constraints remain grounded in [GA4 freshness](https://support.google.com/analytics/answer/11198161?hl=en) and the [change-history API](https://developers.google.com/analytics/devguides/config/admin/v1/rest/v1alpha/accounts/searchChangeHistoryEvents); no edit scope or history request was introduced.

## Release boundary and recovery

Only the disposable local database received the new migration. No production migration, real provider call, deployment, actual environment/flag change, new OAuth permission, commit or unrelated cleanup occurred. Keep existing GA4 gates off until an authorized rollout. Roll back UI/API/worker activation rather than deleting immutable observations or review history; old application code will not understand new v2 observations, so downgrade requires explicit compatibility planning.

D1 is unchanged: a normally completed diagnosis with insufficient evidence for actions is delivered, consumes one point, and is not refunded. Evidence collection/review remains free and is not a new paid report.

This closes the approved evidence-explanation/manual-review slice, not P5/P6 or the full v22 plan.
