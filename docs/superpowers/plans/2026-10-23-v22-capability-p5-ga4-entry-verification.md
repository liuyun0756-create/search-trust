# P5 GA4 owner entry — local verification

## Delivered scope

Continues the previously approved persistence step with report-page confirmation, scope/window preview, status and bounded dispatch. [Design and execution scope](../specs/2026-10-23-p5-ga4-owner-entry-design.md). Brainstorming scope review kept this inside the accepted workflow; React and local web-testing guidance informed the component, request recovery and browser checks. No new marketing or pricing promises.

- New independent default-off `V22_GA4_COMPARISON_COLLECTIONS_ENABLED` gate. Frontend additionally requires the existing capability-dispatch, implementation-record and comparison flags; backend/API/worker additionally require comparison and capability-execution flags. Existing GSC collection flag is not needed for GA4. No actual environment flags were changed.
- Owner-authenticated BFF derives user identity; same-origin POST, bounded request/response bodies, strict schemas, no-store replies, redirect rejection and internal authentication remain in force. Separate GA4 route and projection cannot enter the legacy GSC comparison parser.
- Read-only SQL context checks owner/report/delivery permissions, supplies the latest implementation and fresh scope candidates, and lists at most 20 task IDs. The backend resolves each candidate through existing permission/scope/checksum checks and revalidates every stored job/qualification before projecting it. No token, raw source rows or provider error body is sent to the browser.
- Report panel uses the selected implemented action and 7/14/28/90-day period length. It shows confirmed GA4 property, website hosts, Organic Search channel, observed property timezone, scope-observation date and before/excluded/after windows. An optional exact landing path rejects URLs, query strings, fragments and whitespace. Waiting windows, stale implementation and unavailable scopes block confirmation with actionable messages.
- Confirmation starts unchecked and resets on scope, path, action, window or context changes. Initial load/status refresh only reads metadata. Uncertain acknowledgements retain the exact request ID and original selection in session storage; explicit recovery resubmits that same ID, which retrieves the persisted job or safely retries the original request. A pending acknowledgement blocks a different new request. Existing single-active-task and single-claim gates prevent duplicate provider execution.
- History distinguishes queued/running/failed/collected. Successful collection is labelled **not yet comparable** and shows daily coverage, processing completeness and event-history limitations. Per-metric details use readable explanations rather than internal error codes. No GA4 use-in-comparison button, delta, uplift or causal result is introduced.
- Worker scans persisted requests only, uses deterministic GA4-prefixed ARQ IDs, one try, 315-second outer timeout and the existing 240-second provider attempt. Broker source is explicitly GA4. Redis retains no worker result payload; dedicated HTTP client closes on shutdown.
- Migration 66 extends ID collision protection between GA4 and existing GSC/sync/snapshot/analysis IDs, including reverse insertion, while preserving ordinary sync-to-snapshot reuse. This prevents one operation from using another operation's logical-job budget. Only the disposable local database receives the migration.
- Ordinary snapshots, GSC collection/comparison behavior, report content, implementation records and credit balances are unchanged by collection. D1 remains: a completed diagnosis with insufficient evidence for actions is delivered, consumes one point and is not refunded. GA4 collection itself is free and not a new paid review.
