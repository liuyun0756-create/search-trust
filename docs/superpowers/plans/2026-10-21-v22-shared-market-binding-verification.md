# P2 接续：跨 Case 共享搜索来源绑定

日期：2026-10-21。承接获客入口之后的来源冲突修复。未部署，未启用新入口；P2 整阶段仍未完成。

## 已完成

1. 新获客准备把 SERP 的 Case 存储引用与原始共享来源 ID 分离。独立引用由 Case ID + 原始来源 ID 确定生成；不是改写原始 snapshot ID。
2. 原始 SERP payload、来源任务、内容摘要、原始采集/失效时间，以及竞品的 market 引用保持不变。证据查找核对准确的 Case 绑定，同时兼容旧直接引用。
3. 新增不可变共享来源登记及 Case 引用关系，来源 ID 不能被不同正文、来源任务、摘要或失效时间覆盖。全局登记表没有向用户或普通 service role 开放直接读写。
4. SQL 准备外层按 Case → job → 来源顺序锁定和验证，再调用原准备事务。绕过外层的旧核心函数不再授权给 service role；后续冻结/recipe 失败时，新增来源和绑定一起回滚。
5. 修复缓存来源 ID 原先仅由搜索输入摘要决定的问题：未来新采集的 ID 包含原始内容 SHA-256（其中包含来源任务/时间）。有效缓存仍原样返回，包括旧格式 ID；过期后的新采集不会重新占用上一份证据的 ID。
6. 两个不同 owner/Case 复用同一来源的持久化和读取通过隔离测试，各自拥有独立证据引用，且重放不新增扣点。

## 范围与兼容

- 新 Case-local 存储引用目前用于新版获客准备；没有迁移旧报告、旧来源或私有授权来源，也没有声称修复旧生成路径全部跨 Case 存储行为。
- 缓存新采集 ID 修复属于共享采集层，旧流程未来新抓取同样采用该身份规则；已有缓存、来源和报告不重写。
- 不改变缓存 TTL 或来源资格，不把共享资料当作客户授权数据。正文依旧按 Case 保存，全局登记仅保存不可变来源头部和摘要。
- 不改变计费：正常完成无行动的诊断消耗一点；技术失败按原工作流补偿一次。
- 本地实际 FE dispatch/intake、BE capability execution/intake 均 false；未远程执行迁移，未修改秘密或部署配置。
