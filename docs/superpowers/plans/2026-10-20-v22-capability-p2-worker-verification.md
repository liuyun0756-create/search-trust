## 实际接通

1. 新增 `20261020130000_freeze_v22_capability_generation_recipe.sql`：在已预留一点、已确认业务范围的任务下，原子保存四类公开快照、冻结 manifest、保存生成 recipe。私有 GSC/GA4/可选官方 GBP 必须引用原授权快照，不能通过 prepare 插入。
2. recipe 只保留业务/规则上下文、公开来源 binding、共享搜索元信息和无正文的私有来源 header，不复制 normalized_payload 或临时 raw_payload。SQL 从固定快照恢复原完整输入，并比较完整生成 canonical 字节与原摘要；不改用最新快照。
3. `SupabaseCapabilityInputRepository` 提供有界 prepare/resolve。活动输入复核 job/Case/manifest/代次、原收费、来源健康/匹配/有效期和授权。内存输入封印不随复制/重建模型转移，变动后不能继续执行。
4. `CapabilityV22Executor` 接入实际 `V22ExecutorRouter`、`execute_v22_job` 和 Redis 状态。公开与服务分别走已实现的规则/检查点，再调用上一批事务完成适配器；0–3 行动不凑数，不增加 provider/model/debit 调用。
5. 独立 `V22_CAPABILITY_EXECUTION_ENABLED` 默认 false；本地实际读取也为 false。只有显式启用并有存储/回调配置才注入新执行器和专用 HTTP 客户端。旧两种请求保留，未知/混合字段拒绝；不存在新版公开提交 API。
6. Redis 可以保存完整新报告；GET/SSE 仅暴露 `v22_capability_task_status_v1` 完成引用，不暴露输入清单、私有来源正文或内部成本。新增单独 runtime schema/fixture 与 FE 校验器，旧 API bundle 不改。
7. 新终态裁决 RPC 及 coordinator 接入 worker、超时与 stale 巡检：SQL 已成功则恢复报告，SQL 确认技术失败则原子补偿一次，数据库结果未知则不在 Redis 虚报失败。已提交旧代次结果在后续代次可恢复，但活动输入仍必须同代。

该分支默认关闭；目前真实 UI 提交、旧收集器入口和新报告阅读/编辑/PDF/分享路由尚未切换。下一步必须接入输入准备/排队调用与对应报告页，不可以只开 worker 标志就宣称用户新流程可用。
