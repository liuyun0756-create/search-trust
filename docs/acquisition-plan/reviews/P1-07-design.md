## 1. 已核对的现状与版本边界

后端 `capability_priority.py` 已按 HTTP/noindex 规则 ID 将行动放入最高优先层，但没有检查这条技术依据自身的 status/confidence；`apply_priority()` 截取前三条后仅保留其他候选的排序摘要，不能据此还原完整步骤与材料。前端 `CapabilityDeliveryEditor` 只能编辑、排序和隐藏已入选行动；Python、TS 及数据库保存路径均限制行动身份与系统前三条相同。不能只加一个前端按钮。

拟新增 `v22_capability_public_v12`、报告 schema `2.2.7`、排序 `v22_business_priority_v3`、交付修订 `v22_delivery_revision_v3`，仅新获客报告启用；v11 及更早报告、service 链路和已批准交付继续原路径，冻结输入/证据/旧输出不改写。新增迁移同步 freeze/store/save 白名单与替换校验，沿用目标缺失即 raise 的迁移保护；不执行生产迁移。

## 2. 技术门槛与弱依据

- **资格先于排序**：仅既有 HTTP/noindex 规则实际触发，且同一技术发现为 `kind=fact`、`status=confirmed`、置信度 medium/high、`interpretation=supported`、有可追溯证据时，才授予技术优先级。不能借行动内另一条强依据替一条弱技术依据取得资格。HTTP 必须是已检查页面的真实 4xx/5xx；超时、抓取失败、没有状态码仍是 not_checked。noindex 必须是合格页面快照中的显式指令，不能从没有搜索结果推断。
- **顺序**：先约束显式依赖；合格技术行动优先，其他页面建议（标题、CTA 等）后移；非技术行动保留现有业务匹配、证据、严重度、置信度、执行条件与稳定 ID 排序。多项合格技术行动沿用这些次级键，不凭文字或 severity 单独提权。记录取得资格的 finding IDs、完整候选顺序及原因，前后端可确定性重放。
- **弱依据保护**：沿用 P0-07“全部依据都弱才默认隐藏”的口径；新排序将全弱行动置于可默认交付行动之后，留在顾问候选区，不填充客户名额。混合依据仍保留，但弱 HTTP/noindex 不获得技术加权。无法满足依赖的组合不允许交付。已有技术观察只表述“先检查响应/索引设置”，不能声称网站永久不可访问或 noindex 一定设置错误。
- 排序不负责证明未知事实正确；通过既有证据资格和 P1-00 排除规则防止把未检查当错误，再用金标准及反例检查误报。遇到已确认误报或判断冲突先记录并停下，不靠排名掩盖问题。

## 3. 审核位置、替换交互与存储

**位置**：在现有交付审核页的已入选行动卡片之后、审核确认/保存按钮之前，新增“其他候选（N）”区，按完整系统排序列出所有未入选候选（含第 4 条以后；可分页，但不能只存前三条）。显示标题、目标、依据状态、排序原因，展开查看步骤与材料；弱候选明确标“仅顾问可见，需核实”。客户网页、分享页和 PDF 不展示候选池。

**交互**：候选上的“替换已入选行动”要求选择一个现有槽位，展示替换前后对照，再原位交换；无“添加”按钮，0 条不能借此新增，1/2/3 条分别始终保持 1/2/3 条。退出的行动回候选池；新进入行动使用自身材料与证据，不继承被换行动的文案/证据。暂存会话内保留退出行动的编辑，重新选回时恢复；放弃未保存更改需提示。替换清除审核勾选，保存为新修订并重新批准，旧批准版本/分享不变；并发保存沿用 expected_revision 冲突检查。

**结构**：新报告新增 `action_candidates: Action[]`（包含系统已选及未选的完整原始行动，沿用候选数量和报告体积上限，超限明确报错，不静默丢弃）；`actions` 仍为系统默认最多 3 条且必须逐项等于池内原件；trace 新增 `candidate_order` 和技术资格依据。新交付修订仍用 `actions` 保存最多 3 个可编辑副本、`client_action_ids` 表示客户子集，保留 report/source checksum 绑定。服务器校验行动唯一、来自同一冻结候选池、槽位总数等于系统初始数量、材料身份与证据不可改、依赖闭合及先后顺序合法。浏览器传来的候选正文不能替代服务器原件。

**替换约束（待确认）**：有合格技术候选时，不能用普通页面建议换掉最后一条已选技术行动；替换不能移除其他已选行动依赖的前置项。候选不满足当前槽位次序时禁用并说明，可先合法调序再替换，不自动追加前置行动。客户可见子集也要校验依赖，不能用隐藏前置项绕过约束。弱候选替入后默认隐藏；沿用 P0-07 允许 SEO 明确勾选并重新批准后显示，但不会因此获得技术优先级。“恢复系统选择”预览后恢复原组合；单纯“恢复顺序”只排序当前组合，不暗中换回行动。

投影层从候选池解析替入行动的依据和材料，网页/分享/PDF 统一读取批准修订的同一子集，最多 3 条；理由不伪称替入行动原本在前三，也不泄漏内部 ID、采样参数。Python/TS 校验、保存修订 SQL、合约导出和历史兼容测试一起更新。

## 设计确认（2026-11-05，验收人：Claude）：批准实施，附 5 个条件

条件：
1. **技术前置保护改为警告，不能硬性阻止。** 产品决定是 SEO 拥有完整编辑权。用普通建议替换最后一条技术行动时，弹出明确提示（例如“该网站存在已确认的打不开页面或 noindex 问题，替换后客户报告将不再提到它”），SEO 确认后允许替换，并在修订里记录这次确认。**依赖关系的校验仍然硬性执行**，因为不满足依赖会导致报告内容自相矛盾。
2. **分两段交付，中间停一次。** 第一段：后端排序、候选池、合约、迁移、保存校验和历史兼容测试，完成后写 `reviews/P1-07.md` 的第一段交付并停下。第二段在验收通过后再做：审核界面的候选区和替换交互。
