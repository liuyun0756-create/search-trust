## 实现说明

### 触发和范围

遵照用户已确认的优先级：**静态页面已有任何电话、地址或营业时间候选就不调用，即使文字很少。** 阈值取空白折叠后的 **200 个可见字符**，用于区分触发原因；不覆盖“已有联系信息则跳过”。静态响应缺失或不可用标为未检查，不能推断网站没有联系信息。

只取确认后的客户 `BusinessScope.site_url` 和第一个不同的同站目标页；不从竞品或全站目录挑选额外页面。单份任务最多两次 scrape 尝试，失败也消耗次数；检查点重放复用结果，换检查点也受原成本台账限制。没有 key 或成本账本时不调用。`/map` 保持原用法，竞品和服务采集不接入这个阶段。

新快照 `source_kind=rendered` 与静态来源分别拥有 ID、checksum 和冻结记录。数据库通用 `data_snapshots.source_type` 仍为 `site`，但快照 payload、manifest 关联、证据均明确为 `rendered`；没有把渲染 HTML 伪装成静态抓取结果。通过原准备事务保存并还原独立来源，不只存在 Redis 中。

### 结论边界

遵照任务卡新增“结论边界”：

1. 只有静态结论为未检查、且整个静态抽取没有该字段候选时，才补充电话/地址。既有候选因 `identity_unresolved` 而未检查的，保持不变；已确认结论和身份/时间不合格的比较也保持原样。
2. 渲染的 `tel:`、JSON-LD 或文本都只能确认一致；追踪号码不同、地址不匹配、值不可用和失败都不产生 mismatch、缺失或修正行动。
3. 复用 P0-03 的 HTML、JSON-LD、DOM 和文本抽取、电话/地址比较及精确来源回放。邮编只能部分印证，保留实际比对范围。
4. 新证据及相应比较 limitations 使用 `Based on a rendered page...`。失败使用 `The additional page check could not be completed...`，不暴露提供商错误或内部 ID。客户状态标签的进一步细分按任务卡留在 P0-06。

### 版本与兼容

关闭开关或所有页面均跳过时，仍生成 **v6 / manifest v1 / 报告 2.2.2**，不增加空字段。存在独立渲染来源时才使用 **`v22_capability_public_v7` / manifest v2 / recipe v2 / 报告 2.2.4**。2.2.3 已用于复查报告，未复用其版本号。这是为满足全局规则的版本隔离和历史兼容所需的接入改动。

历史 v3/v4/v5 的冻结输出和 v6 现有夹具继续逐字节校验。没有编辑历史输入、evidence、checksum 或旧迁移。后续启用前需部署本次新迁移及配套代码；本次只在本地 PGlite 执行迁移测试。

依据：[Firecrawl 价格页](https://www.firecrawl.dev/pricing)、[v1 scrape 文档](https://docs.firecrawl.dev/api-reference/v1-endpoint/scrape)，2026-11-03 查阅。
