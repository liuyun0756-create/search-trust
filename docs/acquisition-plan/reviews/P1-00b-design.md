## 2. 营业时间解析与比较

### 2.1 输入、用途与身份

拟增加独立、确定性的 `hours_observation_v1` / `hours_alignment_v1`；只在新获客规则集 `v22_capability_public_v11` 开启。无 LLM、无地理编码、无新 GBP 查询。

网站候选来自两类保存证据：

1. 已通过既有实体归属校验的本商家 LocalBusiness 子类 JSON-LD：`openingHours`、`openingHoursSpecification`。跟随已有 @graph/实体绑定，不把评论者、目录商家、Event 或商品的时间归给本商家。
2. 完整、可解析页面中的可见 DOM：`Opening Hours`、`Business Hours`、`Office Hours` 等明确标签与同一容器的列表/表格/相邻段落；不把整页所有数字拼起来。仅有普通 `Hours` 时还需同行有星期/时间且不存在行程或事件语义。隐藏节点、脚本字符串、注释不当可见文字。

每个候选保存原文、URL、快照 ID、字段/节点位置、抽取版本、时间用途、归一化步骤及覆盖的星期。网站 DOM 仍需本商家页面及既有身份资格；身份未解决则 not_checked。GBP 仅使用身份 matched、健康且在比较时有效的快照中 `state=observed` 的 hours/operating_hours。

用途分为 regular_business / office / appointment_only / emergency / tour_schedule / dated_special / unknown：

- 明确紧急服务 24/7、热线 24 小时不能代替普通营业时间。
- tour、departure、start time、duration、group/private tour、出发日期、集合时间、每人价格附近的时间归为团期/行程，排除普通营业对齐；即使包含星期也不例外。
- 同一商家同时有 office 和 emergency 时分开保存。只有 office 时间而 GBP 未说明用途时，可以展示两渠道需要确认的时间差异，必须注明网站是办公时间，不声称全天服务不可用；若两侧用途明确不同则 not_checked，不产生不一致事实。
- `by appointment`、`appointment only`、`by request` 没有固定时段时不等于 Closed，也不等于全天营业；只能保存预约条件，时段对齐 not_checked。固定办公时段附“需预约”时，保留条件；不能忽略条件就给完整一致。
- 日期、节假日、季节性、temporary closure、validFrom/validThrough 另存为 dated_special；本任务不推导节假日历，不与普通每周表混比。普通表若受未解析日期条件限制，也不强行使用。

### 2.2 格式归一化（待批准的具体口径）

内部用 Monday–Sunday 七天、每日若干不重叠的半开分钟区间；每一天单独记录 unknown / closed / open / all_day / appointment_only。未出现的星期保持 unknown，绝不补 Closed。采用商家页面标示的当地墙上时间；不拿搜索采样点推断时区。显式时区不一致或地点归属不清时 not_checked，不擅自换算。

| 输入 | 规范结果/处理 |
|---|---|
| `Mon`, `Monday`, schema.org/Monday；`Mon–Fri`；逗号、and、& 分隔星期 | 固定英文星期词典与完整词匹配；星期范围展开；中英文标点、NBSP、大小写归一，不凭相邻字猜星期 |
| `9:00 AM–5:30 PM`、`09:00–17:30` | 09:00–17:30；统一连字符/破折号及 am/pm 点号 |
| `9–5`、`7–7`（无 am/pm、无可明确确定的 24 小时格式） | not_checked/parse_ambiguous，不猜上午下午；明确 `09:00–17:30` 可按 24 小时格式解析 |
| `12 am` / `12 pm` | 00:00 / 12:00；`24:00` 仅允许作为明确区间终点 |
| `09:00–12:00, 13:00–17:00` | 两个区间；排序并合并重叠/相邻区间，保留中午休息 |
| `22:00–02:00` | 只有明确采用 24 小时格式或两端 am/pm 时，记录跨日并展开到次日；周日跨周一同理。次日有冲突声明时 not_checked，不覆盖原值 |
| 某日 `Open 24 hours` | 该日 00:00–24:00；不外推到其他六天 |
| 普通营业标签下 `Open 24/7` / `24 hours a day, 7 days a week` | 七天全天；孤立品牌广告中的 `24 Hour` 不自动代表七天普通营业 |
| 本商家 `openingHoursSpecification` 的 `00:00–23:59` | 保留原始分钟值及转换记录；拟仅将这种完整日边界作为全天表示用于等价比较，不对普通时段使用分钟容差，不把任意一小时差异抹平 |
| `00:00–00:00` | 不凭相同端点推断全天/关闭，除非同一明确声明另有 Open 24 hours / Closed；否则 not_checked |
| `Closed` / `Not open` | 仅明确对应的星期为 closed；空值、not_returned、抓取失败不代表关闭 |

预算：每候选最多 7 天、每天最多 8 个区间、原文与来源引用分别有界；超过上限、未知格式、冲突、缺标签不截断为“可比较”，统一 not_checked，并保留原因。不同语言暂不猜译，记录不支持格式。

### 2.3 合并和判定

- 相同来源的重复片段只保留一次。跨页面/同页同用途的多个声明一致可去重；同用途自相矛盾时不任意挑一个，记 `not_checked/conflicting_hours_sources`。
- GBP hours 与 operating_hours 分开解析：一项真实 not_returned 时可使用另一 observed 项；两项都 observed 但不相容，或一项不能完整解析时，不静默择优，记 not_checked。
- 可比较条件：实体确认、来源有效、用途可比、双方至少一个共同的明确星期，没有影响该次比较的未解析/冲突。清楚未提供的周末不是解析失败，可以保留未知而比较明确的工作日。
- **不一致**：至少一个双方均明确的星期，其营业区间或明确关闭状态不同；仅报告这些已确认差异，列明未比较星期。Vision-Tech 工作日即可证明差异，不需要猜周末。
- **完整一致**：七天均明确、用途与条件可比且逐日区间一致。
- **部分一致**：已明确重叠星期一致，但未覆盖全周；保留 partial_match 和遗漏星期，不说整周一致。
- **未检查**：未抓到页面、资源超限、无法解析、仅团期、仅预约/紧急服务、没有共同可比较日、身份不明确、时区/用途冲突、过期来源。均不能产出 missing/site_missing/gbp_missing 或 mismatch；没有营业时间也不新增“补营业时间”行动。

All Star 预期依据是**已确认本商家 JSON-LD 普通营业时间与 GBP 的差异**，而不是从紧急服务广告推导普通营业时间；应在 evidence/limitations 明确网站侧是结构化声明。Vision-Tech 使用有 Opening Hours 标签的工作日可见文字。若实施时发现身份归属或同用途声明冲突使两站不满足条件，记录并停下，不能为了检出而绕开资格。

### 2.4 规则、展示与旧版本

拟新增 `v22_public.gbp_opening_hours_alignment`（v1），独立于原四项对齐，不扩大旧 `SiteGbpAlignmentResult.fields` 的四字段约束。内部小时结果通过新模型输出，合并为 v11 报告的一项 `opening_hours` 核对；客户显示状态与 result 分离，沿用 P0-06/P0-07，未检查不显示“不一致”。

## 3. 小站联系页采集

### 3.1 “小站”和联系页的定义

拟把**当前已发现的合规去重站内 URL ≤20**作为小型采样库存，不声称网站真实总量只有 20。发现受截断/上限影响时标注覆盖不完整；仍在已有预算内争取联系页，不把未发现当不存在。>20 的站点维持现有选页规则，本任务不扩大为全站重排。

候选只来自真实已保存/本轮实际获取的首页链接、已获得的 sitemap/站内链接，绝不猜测 `/contact` 或 `/contact-us` 后逐一探测：

1. 规范路径末段是 contact、contact-us、get-in-touch（允许 .html/.htm 形式）；按完整段匹配，不能误把 `/blog/contact-lenses` 当联系页。
2. 或真实导航/页脚锚文本完整表达 Contact / Contact Us / Get in Touch，允许 URL 为其他路径；随后成功页面的 title/h1、ContactPage 或联系区块支持此角色。联系表单是辅助信号，不把任意报价/订阅表单当联系页。
3. robots 禁止、外域、mailto/tel、后台/登录页、片段链接不进入候选；同一最终 URL 去重。URL 安全、域名范围与重定向校验复用现有保护。
4. 冲突时不把“路径看起来像 contact”直接当已核实联系页；候选身份与成功抓取状态分开记录。最多两个联系候选：按导航明确性、路径明确性、较浅路径、规范 URL 排序；首选失败才尝试第二个，不扩大搜索。

### 3.2 发现、页面上限与资源上限

**发现和选页都必须保障联系页，不能只提高 contact 分数。**

- 在普通候选占满队列前检查已获得首页链接并优先安排联系候选。发现预算 D、深页预算 K 继续来自现有请求，总体硬上限仍 D≤500、K≤50；小站在两种预算内给 1 个联系页保留位置，优先于非首页普通页面。保持入口首页位置；D<2 或 K<2 时不得偷增上限或丢弃入口页，记录 contact_not_checked/budget_limit。
- 成功首页本身若具有明确 ContactPage 角色且包含完整联系信息，可承担该位置，不因路径为 `/` 就重复抓一页；仅页脚电话号码不算已经覆盖独立联系页。
- 联系候选结构检查/完整读取均记入现有计数与请求审计；首选失败和第二候选尝试均计数，复用完整响应缓存，不能用重试绕过上限。最终仍最多 1 个强制保留联系页，第二候选仅用于失败替补；其他联系页按原预算普通排序。
- 完整联系页成功读取，即使 noindex 也允许作为本商家的联系信息证据；noindex 不等于联系信息不可用。仅 v11 的联系页槽位有此例外，技术规则仍观察 noindex，后台/登录排除仍生效。

**解决 Volcanoes 的发现缺口（需要本次设计批准）：**

- 已取得的 256 KB 首页前缀未发现联系候选且响应截断时，允许对该首页做最多 1 次 **4,000,000 字节上限的联系链接扫描**；优先复用已有完整首页响应。不对所有站点/所有页面扩大抓取，不请求地图服务。
- 这次扫描只提取完整、可校验的站内联系链接；截断尾部不能产生正文事实。扫描仍超限或链接未出现时记录 contact_discovery_incomplete，不认定“没有联系页”。
- 唯一保留的联系页完整 HTML 读取上限拟为 4,000,000 字节；新的营业时间提取器只针对首页/联系页使用此有界输入。每站时间提取总量≤10,000,000 字节、每页节点≤20,000、深度≤64；完整正文超限或解析中断为 not_checked，不能从不完整周表确认一致/不一致。
- 原有电话/地址等抽取器的 1 MB 限制不放宽，也不因新增扫描改写其判断。4 MB 内容支持必须使用新的 v11 库存/深页模型（拟 `site_inventory_snapshot_v3`）及独立检查点，不让旧 v10 读取扩大后的页面类型或污染旧缓存。
- 新逻辑仅在客户站点启用，竞品采集保留原行为。不能因为 worker 目前共用站点 stage 就把联系页保障扩散到所有竞品。

### 3.3 成本边界

解析/对齐无额外 API 调用；联系人选页优先通常替换原预算中的普通页面，不增加 D/K。最坏新增直接 HTTP 获取为：首页补充扫描 1 次、首选联系页完整读取 1 次、首选失败后的替补 1 次，共最多 3 个逻辑请求（已有缓存则减少；HTTP 重定向按现有每次≤5跳另记请求数）。带宽/运行时间会增加，不把它们说成完全没有资源成本。

本任务不新增 Firecrawl map/scrape、SerpAPI、LLM 调用，**增量第三方 API 费用预计 $0**。现有其他采集阶段的费用不计作免费；新增联系页不能悄悄进入现有付费渲染兜底扩大调用量。联系页新路径默认只用静态 HTTP，渲染需求另报预算，得到批准后才能执行；任何以后增加付费调用的能力要独立默认关闭开关。

## 4. 联系页采集的验证方法

### 4.1 无网络自动化回归（实施后必须实际执行）

使用可记录 URL、字节上限、重定向、缓存及请求数的假 fetcher，测试真实采集入口→发现→选页→保存完整深页→营业时间抽取，而非只测试 URL 正则：

- 不同联系 URL、导航锚文本、重复链接/最终 URL、首页 ContactPage；文章里的 contact 字样、邮件/电话链接、外域、robots、后台 URL 不误选。
- sitemap 先填满、页脚链接靠后、256 KB 截断；用冻结 Volcanoes 首页原字节作本地响应夹具，证明在 1,118,557 字节附近发现真实 `/contact-us` 链接，而不是在测试中把链接提前。
- 接上**单独、明确标注为合成**的联系页响应，证明完整 HTML 进入新快照且产生 hours 观察。不得把此响应写成 Volcanoes 的真实页面或真实金标准。
- 403/404、超时、超限、跳到外域/登录页、联系页仅靠 JS 且静态无时间：保留失败/未检查，不假称成功；首选失败的第二候选有界；重复执行复用新检查点，旧 v10 检查点内容不变。
- 不因 noindex 丢掉已成功取得的联系信息；也不改变 noindex 技术判定；新增路径不调用付费 map/scrape、不影响竞品 stage。
- 所有时间格式、预约、紧急服务、团期、未知日、跨午夜、别名冲突、多门店身份、过期来源、结构化/可见文本冲突，分别覆盖正反例。不能仅根据两个目标站点定制解析器。
