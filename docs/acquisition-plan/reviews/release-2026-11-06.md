#### 正式 v12 不重新生成的依据与边界

这里指正式工作流的恢复/重试入口，不是否认开发者可以手动调用纯函数做离线计算。

- `capability_public_stage.py:22–46` 以 manifest/request digest 构造 checkpoint key，`JobCheckpoints.run_once()`（checkpoints.py:79–87）先返回既有 checkpoint，只有 miss 才执行生成器。校验 checkpoint 自身 checksum，并不按新生成结果重算旧 checkpoint。
- SQL `resolve_v22_capability_analysis_input` 在 job succeeded 时直接返回已有 completed_report；`capability_executor.py:32–33` 原样返回它，不再进入 public generator。
- 已存 report 不可变；store 检查已存在 ID 时拒绝不同 payload，本轮 native 测试实际验证了该冲突。
- 身份复核在 `public_reassessment.py:102` 固定创建 `v22_analysis_input_v3 / v22_capability_public_v13` 的新 manifest/report ID。manifest validator 与 SQL freeze 也保持 v3/v13 绑定，且仍需重新批准。它不是 v12 的原地重新生成路径。
- 因此本轮不对 v12/v13 承诺“新调用纯函数与旧输出逐字节一致”；承诺已存报告不回写、旧checkpoint不重算、旧payload仍可校验和阅读。v1–v11 的既有32份完整字节不变性断言继续保留并通过。
